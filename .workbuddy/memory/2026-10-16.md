### 踩到的坑（重要）
1. **自定义属性不能用「重复声明」兜底**：`--*` 几乎不解析失败，`--sb: max(...)` 会正常覆盖前一条 → 消费点 `calc(var(--sb)+N)` IACVT 退化为 `top:auto`，**不会**回落到前一条。必须用 `@supports (top: max(0px,0px)) { --sb: max(...); }`。全站唯一实例 `pages/tabbar/pet.vue`。影响 iOS 13.0~13.3 / Chrome 49~78。
2. **sticky/fixed 吸附点要跟随 header 高度**：`order/after-sales` 的 `.tabs`（`top: 88rpx`）在 header 加高后会整条被压住（header z-index 30 > tabs 20）。同类排查：随顶栏高度变化的 `top:` 命中 1 处；fixed 顶栏与 scroll-view 硬算各 0 处。
3. **审计脚本曾有两处误判**（都已修）：①把 v1 误报为「已处理」给出 0 待办的假安全感；②把注释里的 `env(safe-area-inset-top)`（如 `goods/detail.vue:974`）误判成 v1 —— 需先剥离 CSS 注释。
4. **sticky 也是 positioned value**：QA 脚本一开始只把 absolute/fixed 当合法，误报了 `.tabs`，人工排除。

## 审计：待付款金额 ≠ 结算页金额 + 券/积分占用与回退缺失（团队 SOP 交付）

### 🔴 迁移文件注释语法坑：MySQL 的 `--` 必须紧跟空白，否则报 1064
本次修复途中**连续踩到两个独立缺陷**，第二个极隐蔽：
1. **版本号撞车**（先发作）：`V20260929_01__add_user_points_frozen.sql` 与既有 `V20260929_01__add_carrier_api_config.sql` 同版本 → `FlywayException: Found more than one migration with version 20260929.01` → 应用整体起不来。这是**构建期/扫描期**失败，SQL 根本没执行。
2. **注释语法错误**（改名后才暴露）：改名为 `V20261016_01` 后，迁移**真的被执行到了**，但报
   ```
   SQL State : 42000 / Error Code : 1064
   Message : ... near '--（历史表名为 schema_history，非 flyway_schema_history），任何 ≤' at line 18
   ```
   根因是注释行写成 `--（…`（双横线**紧邻全角括号**）。**MySQL 只在「双横线后紧跟空白（空格/Tab）」时才当注释**；`--（`/`--文字` 会被当作算术表达式解析 → 1064。
   → **规则：迁移/种子 SQL 的所有注释行一律写成 `--` + 至少一个空格**。写中文注释时尤其容易忘（中文标点紧跟双横线）。
   → 有意思的是，这段注释正是主理人给工程师的说明文字被贴进 SQL 后产生的 —— **不要把解释性讲话原样塞进 SQL 注释**。
3. **二次效应**：脚本失败后每次重启都报 `FlywayValidateException: Detected failed migration to version 20261016.01`（`schema_history` 留下一行 `success=0`）。因 prod 配了 `repair-on-migrate:false`，处置方式是手工 `DELETE FROM schema_history WHERE version='20261016.01' AND success=0;`。失败发生在注释行、ALTER 从未执行，无半完成结构，无需 repair 其它行。
4. 诊断顺序教训：**「改名后仍起不来」不等于「改名没用」**，要重新捞容器日志看**新的**报错，别沿用旧结论。
