## 修复：首页点击海报提示 `Banner [object Object]1`

### 根因
`src/pages/tabbar/home.vue` 把 `@click` 绑在 `<swiper>` 上，方法签名却是 `onBannerClick(idx)`，
把**事件对象**当索引用：

```js
onBannerClick(idx) {
  uni.showToast({ title: this.$t('home.bannerN', { n: idx + 1 }), icon: 'none' })
}
```

`{ n: 事件对象 + 1 }` → 字符串拼接 → `"Banner [object Object]1"`。

**关键事实（本次实测确认）**：uni-h5 的 `swiper` 组件**不会**派发带 `detail.current` 的 click。
在 `@dcloudio/uni-h5/dist/uni-h5.es.js` 里全文搜 `trigger("click"` 只有 2 处，都是 **map** 组件
（25171 / 25195，`trigger("click", {}, {})`）。swiper 的 `@click` 只是属性透传到根 DOM 节点，
H5 下拿到的是原生 MouseEvent（无 `detail`）；APP 下事件结构也不一致。
→ 因此**不能**靠 `e.detail.current` 取索引，`animationfinish` 那套 payload 不适用于 click。

### 改动（`src/pages/tabbar/home.vue`）
- 模板：`<swiper>` 去掉 `@click` 与 `:disable-touch="false"`；click 下沉到 `swiper-item` 内部，
  用 v-for 闭包索引：
  ```html
  <swiper-item v-for="(b, idx) in displayBanners" :key="b.id || idx">
    <view class="banner-item" @click="onBannerClick(idx)">
  ```
- `onBannerClick(idx)`：`Number(idx)` 取索引；若误传事件对象，兜底试 `detail.current`，再不行取 0
  （保留防御，避免以后被改回绑 swiper 又拼出脏字符串）
- `openBannerLink(link)`：链接判定用**纯字符串正则**，不依赖 `URL` 构造函数（APP 端不保证可用）：
  ```js
  const internal = link.match(/^(?:https?:\/\/[^/]+)?(\/pages\/[^?#]*(?:\?[^#]*)?)$/i)
  ```
  - 命中 → 站内页：base 在 `TAB_BAR_PAGES` 里用 `switchTab`（不能带 query），否则 `navigateTo`（fail 时 toast）
  - 未命中且 `^https?://` → 外链：APP `plus.runtime.openURL`，H5 `window.open`
  - 其余 → toast `home.bannerUnavailable`
  - 收紧后的好处：`https://example.com/blog/pages/x` 这种外站路径**不会**被误判成站内页
    （旧实现用 `indexOf('/pages/')`，会切出 `/pages/x` 交给 navigateTo）
- `fallbackBanners` 去掉 picsum.photos 外链（真机常无公网），模板改 `v-if="b.image"` + `.banner-placeholder` 纯色兜底
- i18n：删 `home.bannerN`，新增 `home.bannerUnavailable`（中/英）

### 验证
- `@vue/compiler-sfc` parse/compileTemplate/compileScript 全 0 error/0 tip；6 项断言全 PASS
- 正则实测 7 种形态全部符合预期（含 CMS 真实链接、外站含 `/pages/`、tabBar 带 query、空串）
- `uni build -p app` 两次均 DONE（1m4s / 44s）；产物 `app-service.js` 内确认：
  `createElementVNode("view",{class:"banner-item",onClick:e=>r.onBannerClick(o)})`，`bannerN` 无残留
- 数据核对（`GET /api/v1/cms/banners`）：现网仅 1 条 banner，
  `linkUrl=http://192.168.6.103:5174/pages/goods/detail?id=2105185483541049345`
  → 解析为 `/pages/goods/detail?id=…` → navigateTo ✅；目标商品接口 200（name=001, price=60）

### 遗留风险
- 该 banner 的 `imageUrl` 是**外站** `https://www.bloomwitness.com/wp-content/uploads/pet_safe_placement_1024x768.jpg`
  （实测 200 / 456KB 可用，但真机无公网时会空白）。CMS 里改成 `/uploads/...` 自托管更稳。
- `home.vue` 是 H5 热更即生效；**原生包需重新打包**（`dist/build/app` 已更新）。

### 教训
- `swiper` / `swiper-item` 上的点击一律绑在**内部普通节点**并用 v-for 闭包索引，
  不要指望组件事件 payload（与铁律 8 同源：原生组件的 props/事件不按 Web 语义走）。

## 修复：APP 端 `pages/pet/space-3d` 提示「当前环境不支持 3D」

### 根因（架构级，不是配置问题）
uni-app **vue3 的 APP 端页面 `<script>` 跑在逻辑层**（jscore / V8，`app-service.js`），
那里**没有 `document` / `window` / WebGL**。旧实现直接在页面脚本里
`document.getElementById(...)` + `new THREE.WebGLRenderer()`，并写了
「APP 端 document 可能在 webview 启动早期短暂 undefined，重试 30 次」——
这个前提是错的：**document 永远不会出现**，所以 30 次必然全失败，
最后落到 `envUnsupported` → `当前环境不支持 3D（仅 H5/APP 支持）`。

判定证据（构建产物）：
- `dist/build/app/__uniappview.html` 只加载 `uni-app-view.umd.js` + `app-renderjs.js`
- 页面业务代码全在 `app-service.js`（逻辑层）；视图层没有页面脚本
- 所以 vue3 APP 端 = 逻辑层/视图层分离，DOM 只在视图层（renderjs）

### 改造（方案：整页引擎搬到 renderjs，两端共用一份）
新增/改动文件：
- **新增 `src/utils/pet3d/space3d-engine.js`**：原 `space-3d.vue` 的 2571 行脚本**整体搬入**
  （尺度/碰撞/室内判定/TPS-FPS 相机/摇杆/诊断面板逻辑逐字保留），只做 4 处改写：
  1. `three` / 4 个 loader 由**动态 import → 静态 import**（视图层产线是普通脚本，没有 chunk 加载器）
  2. `ensureLocalModel` 改为可注入（`setModelResolver`）——它依赖 `uni.downloadFile/saveFile`，只有逻辑层能用
  3. `uni.navigateBack` / `uni.showToast` 收口到 `setHostBridge`（视图层不保证有全局 uni）
  4. `initScene` 不再动态加载 three
- **新增 `src/utils/pet3d/create-engine.js`**：把 `pageOptions`（data/computed/methods/生命周期）
  装配成普通对象 —— computed→getter（`three` 桶仍靠 WeakMap 缓存）、methods 直接挂实例、
  生命周期由宿主手动调用；**用 32ms 轮询做增量 diff**，只把变化的 UI 字段推回逻辑层
- **`space-3d.vue` 重写**：模板只留 HUD；`<script>` 变薄壳（下载模型 + 翻译 14 个文案 +
  镜像状态 + 转发指令）；新增 `<script module="pet3d" lang="renderjs">` 跑引擎并**直接绑 DOM 手势**
- **`src/utils/modelDownload.js`**：`resolveRemoteUrl` 改为具名导出（给 APP 端远程兜底用）
- i18n 新增 `petHub3d.engineBootTimeout`

### 关键机制（实测确认）
- **renderjs 块由 uni 单独用 esbuild 打包，不认 `@` 别名** → 必须写相对路径
  （`../../utils/pet3d/create-engine`），否则 APP 构建报 `Could not resolve "@/utils/..."`，
  H5 却是好的，极易漏掉
- H5：renderjs 模块被作为 mixin 合入页面（`beforeCreate(){ this[name] = this }`），
  所以 `this.pet3d === this`；APP：`initRenderjs` 在服务层挂一个**代理**，
  `this.pet3d.onHostCommand(...)` 走 JSON 协议转发到视图层
- 视图层 → 逻辑层：`this.$ownerInstance.callMethod('onPet3dState', patch)`
- **`initRenderjs` / `initModules` / `callMethod` 的实现不在业务包里**，属于 HBuilderX 基座运行时
  （业务包里搜不到这些字符串是正常的，别据此判断"链路断了"）
- APP 产物：`app-renderjs.js` 800KB（含 three + 引擎），`app-service.js` 里**不含引擎**
  （只有薄壳 + modelDownload）；页面选项里 `$renderjs:['pet3d']` + `$renderjsModules:{pet3d:'<id>'}`
- **模型 67MB**（home.glb 6.7MB + 0.fbx/1.fbx 各 30MB）：必须逻辑层 `ensureLocalModel` 先落地，
  再把 `{primary(本地), fallback(HTTP)}` 交给视图层；引擎在 GLTF/FBX 加载失败时自动回退 HTTP
  （APP 视图层可能读不到 `_doc/` 本地文件）
