#### 冲突 A：色条取色的权威源 —— 最终采纳「`color_hint` 非权威」

| | team-lead 早期指示（基于 Phase 1 v1.3） | **Phase 1 v1.6（最终采纳）** |
|---|---|---|
| 结论 | 「以 DB `mo_brand_ip.color_hint` 为权威」→ 废弃前端 4 个孤儿色 + 全站迁移（**破坏性变更**） | 「**`color_hint` 不是权威**，色条取色一律以**语义线**（`variables.scss`）为准」 |
| 后果 | 破坏性变更，迁移所有引用点 | **不需要破坏性变更** —— 前端 4 条色值保持权威，只需新增 `ipToLine` 映射层 |

**支撑证据（team-lead 与 visual-architect 分别独立复核，我汇总）：**

| # | 证据 | 出处 |
|---|---|---|
| **E1** | 建表注释写的是 `COMMENT '主色提示：#DBC98A'` —— **注释里的示例值恰好 = LUNA(2) 的实际值** → 这是"随手填了个示例值"的自由填充列，注释从未声明它对应语义产品线 | `migration-combined-final.sql:3437` |
| **E2** | ATLAS(3) 填的是 `#2E2B29` = `--color-text`（Charcoal **正文色**）→ 把正文色填进"主色提示"列，本身说明该列无规范约束 | 同上 INSERT |
| **E3** | 前端 `--color-home: #d9b4b0` 在 DB 四条值里**独缺**，且顺序错位 3/4 | 同上 |
| **E4** | `color_hint` / `colorHint` 在 **Java 后端 + admin 前端 grep 均无命中** → 纯数据字段，**无任何运行时消费点** | Java + admin 全量 grep |
| **E5** | **admin 后台没有 `mo_brand_ip` 管理页，也没有 `color_hint` 的任何配置入口**；`VARCHAR(16) NULL`、**无 CHECK、无索引** → **从未被约束、从未被维护、从未被使用** | `moyuyo-admin/src` 全量 grep |

**决定性的一击（我的论证，team-lead 认可）**：
> Phase 1 v1.6 连「**IP → 语义线**」这个映射本身都标注为**推断**（DB 里根本没这一列）。既然如此，把另一个推断值（`color_hint`）升为"权威"就是**自相矛盾** —— **两个推断不能互相佐证**。

**另有一条绕不过去的硬约束**（visual-architect 补充）：
> 即使决定"以 DB 为准"，**DB 侧也必须先改 2 条数据**才可用 —— OLIVE(HOME) 的 `#ABB9AD` 是 `--color-gear` 的值（**HOME 在 DB 里根本取不到色**）、ATLAS(PLAY) 的 `#2E2B29` 作 chip 色条在浅底上仅 **1.05:1 物理上不可见**。→ "以 DB 为准"的第一步仍然是改数据，改完就等于"语义线为准"。

**最终裁定（team-lead 2026-11-19）：采纳方案 ③「修数据，不迁就数据」**
> 取色链路**不变**（色条仍取语义线）+ **DB 4 行 UPDATE**（SQL 原文见 Phase 1 §4.4.2）+ **前端改动 0 处** + **代码引用点迁移 0 处**

| 项 | 内容 |
|---|---|
| **前端** | **0 处改动**。`ipToLine` 链路不变，`color_hint` 仍不读 |
| **后端** | **DB 4 行 UPDATE** —— 把 `mo_brand_ip.color_hint` 的 4 个值改成对应语义线色，**让 DB 与前端一致** |
| **代码引用点迁移** | **0 处** —— 因为 `color_hint` 无任何运行时消费点（E4） |
| **理由** | team-lead 复核 E1–E5 后明确：原指示里「运营在后台配的就是权威」**被 E5 直接推翻**（admin 后台根本没有配置入口）。既然这列**从未被维护**，那就把它**修对**，而不是让前端去迁就一个错值 —— **修数据的成本（1 张表 4 行）远低于迁就数据的成本** |

**「修数据」方案的实测依据（我独立复算，与 visual-architect 提供的数字完全一致）：**

| 校验 | 结果 |
|---|---|
| 4 个 DB 现值作 **chip 文字色** on `#F0ECE6` | MILO **2.66** ❌ / LUNA **1.40** ❌ / ATLAS **11.95** ✅ / OLIVE **1.74** ❌ —— 三条不达标 |
| ATLAS 现值作**色条** on 浅底 `#F6F2EE` | 12.62 ✅ |
| **ATLAS 现值作色条 on 深底 `#1A1816`** | **1.26:1 ❌ 物理上不可见**（on `#322E2A` 更差，仅 1.04:1） |
| **语义线 4 色作色条 on 深底 `#1A1816`** | **8.66 / 10.74 / 5.65 / 9.36** —— **全部达标** |

> 最后一行是**修正方案有效性的证明** —— 不只是"改完更好看"，而是"**改完深色模式才真正可见**"。若沿用 ATLAS 现值，深色模式下该 chip 的色条会**物理上看不见**。这条比"色条要取语义色"更有说服力，已加为验收项 38。

**损害范围已核实为零**：team-lead 查过原型 —— `line-chip` 四条色条全部取语义线 token（`--color-care/gear/play/home`），`color_hint` 零引用，`LINES` 映射也是语义线。**损害止于规范文档**。

#### 冲突 B：slogan 斜体 —— 最终采纳「全 App 取消斜体」

| | team-lead 早期指示 | **Phase 1 v1.5+（最终采纳）** |
|---|---|---|
| 结论 | `font-style: italic` **仅在 `locale === 'en-US'` 时生效** | **全 App 不使用斜体**（`font-style` 仅 `normal`），中英文都正体；编辑感由字距与细分割线表达 |
| 附带收益 | 需打包 `playfair-display-latin-italic.woff2` | **省下一个字体文件**（v1.6 §6.6.2 明确不需要） |

**支撑理由**：
1. **渲染正确性**：斜体是字体的**真实字形**，伪斜体是**算法倾斜**；汉字笔画倾斜后重心偏移、撇捺角度失真 → 中文排印里几乎总是负面的
2. **必然发生**：Playfair 无 CJK 字形 → 中文必然落宋体 → 必然伪斜体 → **是渲染缺陷，不是设计**
3. **跨语言一致性**（visual-architect 补充的最硬一点）：若英文真斜体、中文正体，**同一个 slogan 在两个 locale 下会呈现两种视觉性格**。slogan 是品牌收尾位，用户切换语言时看到的是同一位置的东西，**视觉性格不该变**。取消斜体让两个 locale 共享同一套排版语言（细线 + 字距 + 对称留白）—— 与 §3 跨页一致性锚点表同源
4. **减法出高端感**：编辑感来自**排版秩序**而非字形倾斜，与 Phase 1 §2 品牌论证同源
5. **实打实的收益**：在 ≤120KB 字体包上限下，省掉一个 italic woff2 = 少一份体积 + 少一份加载失败风险

**最终裁定**：**采纳 Phase 1 v1.5+**（全 App 取消斜体）。team-lead 原指示作废。

## 0. 结论摘要（TL;DR）

> 已对齐 Phase 1 **v1.2**。以下为最终结论，与 Phase 1 无冲突。

| 项 | 结论 |
|---|---|
| 首页首屏任务 | **建立品牌信任 + 暴露三条路径**（逛今日精选 / 按任务走 / 按品类找）。Hero = **当日主推（运营位）+ 恒定品牌 kicker 锚**，不是纯品牌主张 |

| 会员语义 | **成长值 → 等级 → 权益** 是一条纵向链；**积分**是独立的横向货币；唯一接口是「等级 → 积分倍率」。会员卡 = **身份象征（主）+ 积分入口（次）**。Phase 1 v1.4 最终裁定：56rpx **等级名**（英文，展示体）+ 24rpx 中文副标（sans）+ 刻度条右端 22rpx **精确成长值** + 动态 tip；**积分余额完全移出卡面**，只在钱包带第 2 格 |

## 1. 阅读约定

### 1.1 状态机记号

| 记号 | 含义 |
|---|---|
| `S-XXX` | 状态标识符，前端可用作 `state` 字段值或 class 前缀 |
| `→` | 状态转移，箭头旁标注**触发条件** |
| `■` | 终止态（离开该页 / 不再有返回路径） |
| `⊘` | 该状态在本页不存在 |

### 1.2 状态分类（与 Phase 1 §5 各页第 4 小节对齐）

| 类别 | 定义 | 全局表现规则 |
|---|---|---|
| **常态** | 有数据且用户已登录（或本页无需登录） | 正常渲染 |
| **加载** | 请求在途 | 骨架屏，**不出现文字态 loading**（Phase 1 X6） |
| **空** | 请求成功但业务上无内容 | 图形 + 一句解释 + 一个动作（Phase 1 P5 / X6） |
| **错误** | 请求失败 | 图形 + 具体失败项 + 区块级「重试」，**不清空其它区块** |
| **未登录** | 需账号才有内容 | 页内引导段，**不弹窗**；仅在用户点击具体动作时才 modal |
| **局部** | 单区块子状态（未读 / 已置顶 / 离线条 / 加载更多） | 行内或区块内呈现 |

### 1.3 全局约束（继承 Phase 1，本阶段只补充交互语义）

- Phase 1 §7 的 **X1–X7 反面清单**是实现的静态自查项，交互设计不得引入违反项。

| 产品线资产放哪 | **三处同款 chip**，形成跨页一致的资产：① 首页 Curated Shelf 区块头下的**产品线索引行**（4 chip，可横滑，点击 → 分类页 `?line=`）② 社区帖子头部下方（**系统自动打标**）③ 分类页接受 `line` 参数并在左侧栏顶部用同一 chip 组高亮 |

#### 2.1.2 理由

**为什么 Hero 不能是纯品牌主张**：Hero 的图、标题、标签、跳转全部来自 CMS（`cmsApi.getBanners`），是运营资产。若 Hero 承载品牌主张，则每一张运营 banner 都必须承担品牌一致性责任——运营排期一乱，品牌即失控。而且品牌主张是**静态**的，用一个每 3 秒轮播的位来承载静态命题，本身就是错配。

**为什么 Hero 也不能是纯促销位**：Phase 1 §2.2 论证 3 明确本品牌「不是促销轰炸」。如果首屏唯一焦点是一张打折 banner，视觉上与所有电商首页无差别，`Linen & Brass` 的编辑部调性在第一眼就失效。

**折中方案（Hero = 品牌 kicker + 运营主推）**：
- 品牌句放在**位置**上而非**内容**上：kicker 恒定 → 每帧都带品牌句 → 品牌在场但不占运营位。
- 运营主推通过**标题 / 图 / 标签**表达 → 运营有完整自由度。
- 兜底（banner 接口失败）时：整块换成 `--brand-gradient-hero` 品牌渐变 + **同一句 kicker** → 品牌句在错误态依然成立（这是"品牌句写死"的第二个收益）。

**为什么产品线不进金刚区**：
1. **维度不同**：分类/会员/领券/限时都是"我要做的事"，Care/Gear/Play/Home 是"商品的归属族"。把两个维度塞进一排 4 格，用户会误以为「Care」也是一种"事"。
2. **生命周期不同**：金刚区是运营位（随时替换、跟活动）；产品线是品牌资产（长期稳定、需沉淀认知）。混排会同时削弱二者 —— 运营位显得不可靠，品牌资产显得像活动入口。
3. **Phase 1 已定金刚区"降级为细窄功能条、无卡片外壳"**，它的视觉权重本就低于 Hero。产品线作为品牌资产需要**可被记住的重复出现**（首页一次 + 社区一次 + 分类一次），而不是在首屏占一格后消失。

### 2.2 Q2 · 会员体系的语义分层；会员卡是"身份象征"还是"积分入口"？

#### 2.2.1 裁定

**四者关系**：

```
成长值 growthValue ──(只增，跨阈值)──► 等级 level ──(映射)──► 权益 privileges
                                                                          │
                                                    等级 ──(倍率)──► 积分 points ──(可消耗)──► 兑换/抵扣
```

| 概念 | 定义 | 是否可消耗 | 唯一职责 |
|---|---|---|---|
| **成长值** | 消费 / 行为累积值，只增不减 | 否 | 推进等级 |
| **等级** | 成长值的分箱结果（NORMAL / SILVER / GOLD / PLATINUM / DIAMOND，阈值见 `membership.vue` `growthThreshold` 500 / 2000 / …） | 否 | 身份标识 + 决定权益与积分倍率 |
| **权益** | 等级映射出的能力集合（现有 i18n `member.privileges`：社区互动 / 基础健康记录 / 专属折扣 / 免运费 / 优先客服 / 独家内容 / 生日礼包） | 否（消耗的是**资格**，不是数值） | 描述"这个等级能得到什么" |
| **积分** | 可获得（消费 / 签到 / 任务 / 会员倍率）、可消耗（兑换 / 抵扣）、**会减少** | **是** | 唯一的可流通货币 |

**关键澄清（这是整张卡不该挤三件事的根本原因）**：
- 成长值与等级是**同一条纵向链的两端**（一个是连续量，一个是其离散化）。
- 积分是**独立的横向货币**，与等级的唯一接口是「等级 → 积分倍率（`pointsRate` 1.0 / 1.1 / 1.2 …）」。
- 权益是等级的**纯函数**，不独立累积。
- 因此「成长值 / 等级 / 积分 / 权益」中，**只有一个是可消耗的数字（积分）**，另外三个是身份。混在一张卡上等于把身份和钱包画在同一张钞票上。

**会员卡定位**：**身份象征（主）+ 积分入口（次）**。

- 保持 Phase 1 §5.4.3 的金色主角地位不变。理由：若降级为「积分入口」（纯工具），它就不配 `--brand-gradient-vip` 整块渐变 + 唯一 `--shadow-brand` + 唯一 56rpx 展示体数字；工具型入口应该是无底色的小行（Nielsen「识别优于召回」：用户要认出"我是谁"，不是查"我有多少分"）。Phase 1 的视觉方案是按身份象征设计的，**本裁定与之一致**。
- 但 **Phase 1 §5.4.2 卡面写的是 `Points: {points}` 的 56rpx 数字 —— 这把"钱包"放在了"身份"的位置上**，与身份象征定位矛盾。需要修正（见下表）。

### 2.3 Q3 · 社区的商品化边界与"头条位"分配机制

#### 2.3.1 头条位归属

| 项 | 裁定 |
|---|---|
| 谁占首帖 | **编辑策展位**。由运营在后台指定一条内容作为「今日刊首」；接口下发 `leadPostId` 或 `isLead` 标记 |
| 后端暂不支持时 | **降级方案**：取推荐流返回的第一条，由编辑侧通过推荐排序保证；前端**不做任何本地判断**（不按点赞数排、不按时间排、不随机） |
| 是否参与算法竞价 | **否**。当前版本**不设付费头条** |
| 商业化边界 | 若未来引入商业推广：① 头条位**必须让位给官方策展**（头条是品牌信用位）；② 商业内容降级到碎片流前 2 位，且**必须标注「广告」**；③ 商业内容**不得使用产品线 chip**（避免用品牌分类给广告背书） |

**理由**：Phase 1 给 community 定的人格是「杂志信息流 / 编辑式社交墙」，刊首是**编辑权的物理体现**。若让算法决定刊首，社区会在 3 个月内滑向抖音化 —— 大量同质视频、无限下拉、首屏无差别 —— 违背 P1（一屏一主角，主角必须是**被挑选**的那一条）。而"最热"这件事已经在首页「今日爆款」tab 里兑现了，社区不需要重复。

#### 2.3.2 帖子能否挂商品卡

| 项 | 裁定 |
|---|---|
| 能否挂 | **能，但严限**：单帖**最多 1 张**商品卡 |
| 挂在哪 | **帖子尾部**：正文之下、互动行之上。**不挂头部**（头部是作者身份区），**不挂图片之间**（破坏 P4「图片是主角」） |
| 卡片形态 | **横向条**，非竖排大卡。缩略图 96×96rpx + 名称（26rpx 单行省略）+ 价格（28rpx 字重 600 `--color-text`，**不用金色**）+ 右侧 `luc-chevron-right` 24rpx tertiary。高 ≤ 120rpx |
| 谁能挂 | **仅作者本人主动挂**，在发布页选商品。**系统绝不自动挂** |
| 为什么不做自动挂 | 自动挂 = 系统猜"这个帖适合推什么货" = 帖子变成广告位，信任崩塌；且违反 Phase 1 P4（商品图会与帖子封面争主角位） |
| 明确禁止 | ① 帖子内嵌商品列表 ② 帖子头部贴商品条 ③ 帖子本身就是商品详情 ④ 评论区分页商品推荐 ⑤ 商业帖使用产品线 chip |

**理由**：一张商品卡是**第二主角**。Phase 1 P1 要求一屏一主角；一张 1:1 商品图足以在 4:3 帖子封面旁建立第二个视觉重心。所以：限 1 张、横条形态、位置在尾部（视觉层级最低位）、作者主动。

#### 2.3.3 产品线 chip 是用户手选还是系统自动打标

| 项 | 裁定 |
|---|---|
| 默认 | **系统自动打标** |
| 作者可否改 | **可改**（发布页 / 编辑页可见当前自动标注结果，可手动改）；手动改后**以作者选择为准** |
| 是否必填 | **否**。发布页**不出现**"请选择产品线"这类必填项 |
| 无匹配时 | **不显示 chip**（不猜、不随机分配、不显示占位色块） |
| **数据来源（Phase 1 v1.5 已确认是真数据）** | **后端已在自动打标**：帖子表 `mo_community_post.ip_code` VARCHAR(32) NOT NULL + `KEY idx_ip_code`，`CommunityPostEntity.ipCode` 字段存在，发布时由 `CommunityServiceImpl:192` **自动从关联宠物的 `preferred_ip_code` 继承**。前端只差**读取**，不需要作者选。⚠️ **字段名 ≠ 语义**：库里存 IP 名（`MILO`），chip 色条要语义色（Care/Gear/Play/Home）→ 必须经 Phase 1 §4.4.2 的唯一真值源映射表转换 |

**打标来源优先级**（强 → 弱，⚠️ 第 2 位是后端现行实现）：

| 优先级 | 信号 | 状态 | 说明 |
|---|---|---|---|
| 1 | 帖子挂的商品所属 `brandIpId` | ❌ 当前不可用 | 帖子不能挂商品（§2.3.2 已裁定不开放） |
| 2 | **关联宠物档案的 `preferredIpCode`** | ✅ **后端现行实现** | `CommunityServiceImpl:192` `entity.setIpCode(pet.getPreferredIpCode())`。**这条已有真实数据** |
| 3 | 帖子话题标签映射（话题 → IP） | ⚠️ 需映射表 | 话题是自由文本（`mo_community_post.topic VARCHAR`），后端无映射关系 |
| 4 | 作者历史发布的主 IP | ❌ 后端无此聚合 | 需自行计算 |
| — | **无匹配** | — | **不显示 chip** |

**理由**：
- **纯用户手选会失败**：绝大多数用户不会填 → chip 覆盖率极低 → Phase 1 §5.2.2「内容进入品牌产品线体系」的设计意图落空 → 品牌资产无处安放（这正是 Phase 1 Q1 的顾虑）。
- **纯系统黑盒会翻车**：自动打标但不可改，用户看到"我的洗护帖被标成 GEAR"会失去信任。**可改**是必须的。
- **自动打标 + chip 不抢焦点**（高 40rpx、20rpx 字、`--radius-xs`）满足 Phase 1 P4，chip 是图注级元素而非第二主角。

**⚠️ Phase 3 的 1 个前置依赖（唯一阻塞项）：**

| 事项 | 详情 |
|---|---|
| **需要什么** | 后端 `CommunityPostVO` 透出 `ipCode` 字段（当前 VO 17 个字段里没有） |
| **工作量** | 后端 **1 行**（VO 加字段 + converter 赋值），`ip_code` 列、`idx_ip_code` 索引、`CommunityPostEntity.ipCode` 字段**全部已存在** |
| **前端** | `community.vue` / `detail.vue` 读 `p.ipCode` → 查 `BRAND_IP` 表 → 渲染 chip |
| **若不能改后端** | **降级方案**：chip 不显示。⚠️ 但请注意这与"后端没这字段"是两回事 —— 字段在库里、有索引、发布时已写入，只是 VO 没透出。**Phase 1 v1.5 已撤销原先的「⛔ 待后端字段 / 原型不得假数据硬编」结论** → 原型**可以用真实 IP 数据映射到语义色条**呈现 |
| **chip 上的名字** | Phase 1 §4.4.2：**语义产品线名**（如 `GEAR 出行`），由 `ipToLine` 派生，**不直接显示 `MILO`**（那是 IP 名不是产品线名）；4 条产品线名需入 i18n（中英两份），沿用 `goodsDetail.specProductLine` 所在字典组 |
| **chip 色条** | 按**语义线**取（`ipToLine('MILO') → 'gear' → --color-gear`），**不按 IP 名取、不读 DB `color_hint`**（Phase 1 v1.6 E1–E4 四条证据） |
| **⚠️ 前置确认** | `ipToLine` 的返回值在**产品侧书面确认前是推断值**（DB 无「IP ↔ 产品线」列）。Phase 4 实施前置条件 |

**作者手动改后的视觉处理**：不加特殊描边（会引入新 token）；在**发布/编辑页**用一句 22rpx tertiary 提示「已手动标注」即可。

### 2.4 Q4 · 未读与角标的全局策略

#### 2.4.1 什么算"未读"

| 类别 | 算未读？ | 说明 |
|---|---|---|
| 私信会话的未读消息 | **✅ 算** | 唯一进 tabBar 数字的 |
| 通知条目（互动 / 订单 / 系统） | **✅ 算** | 进铃铛红点与通知段红点 |
| 待处理订单（待付款 / 待收货 / 待评价） | **✅ 算** | 只在 user 页订单带呈现，**不进 tabBar** |
| 帖子点赞数 / 评论数 / 浏览量 | **❌ 不算** | 社区互动**不外溢为全局未读**，只在帖子内以点赞态呈现 |
| 粉丝数 / 关注数变化 | **❌ 不算** | 计数不是未读 |
| 会员等级变化 | **❌ 不算** | 身份变化用身份视觉（等级 chip）表达，不用红点 |

#### 2.4.2 红点 vs 数字 vs 金色

**判据一句话**：**用户需要知道"有多少"才能决定下一步 → 数字；只需要知道"有" → 红点。**

| 位置 | 形态 | 规格 | 理由 |
|---|---|---|---|
| **tabBar · messages** | **数字** | `1–99` 原值；`>99` 显示 `99+`；`0` 不显示 | 私信是"要处理的事"，数量决定优先级与是否立刻回 |
| **tabBar · 其他 4 个** | **不显示** | — | 未读只在 messages 产生（社区互动不外溢）。这是对 Phase 1 "角标规则不统一"问题的根治 |
| **顶栏铃铛**（home / community / messages） | **红点** | 12rpx 实心圆 `--color-danger`；**无数字** | 通知是"知道有就行"；铃铛承载多类型通知，总数无意义 |
| **通知 4 宫格内** | **红点** | 12rpx，贴图标底右上角 | 同上 |
| **私信会话行** | **金色竖条 + 字重差** | 6rpx 通高金色竖条 `--color-primary` + 标题 600/400 | Phase 1 §5.3.3 已定：这是行内状态不是角标 |
| **订单带 4 格** | **小数字** | pill，≤9 显示数；`>9` 显示 `9+`；20rpx `--color-danger` 底 + 白字 | 订单数少但需精确（"去付款"/"去评价"） |
| **社区帖子 · 点赞态** | **图标变红** | `luc-heart` `--color-danger` | 已点赞是状态不是未读 |

#### 2.4.3 红点与金色的语义分工（全局硬规则）

> **红点 = 外部来源的新东西**（通知、待处理订单）
> **金色 = 与"我"有关的未读与身份**（私信未读竖条、会员等级、会员卡、进度刻度、tab / 分区指示器）
> **角标一律不用金色。**

两者语义域不重叠，因此可以并存而不打架。同时遵守 Phase 1 P2「金色点到为止」：金色只出现在 §2.4.3 列出的身份语义位，**角标位（铃铛红点、订单数字 pill）一律 `--color-danger`**。

#### 2.4.4 通知中心与私信是否还需要两个独立入口

**裁定：保留两个入口，但收进同一个收件箱容器，且从"跨页跳转"改为"页内切换"。**

| 现状问题 | 裁定 |
|---|---|
| Phase 1 §5.3.1 已定"通知聚合 4 宫格 + 私信列表合并进一个 `--surface-elevated` 容器" | **保持** |
| Phase 1 Q4 提出的"4 宫格点击后跳到另一个页面的对应 tab，成本高" | **消除跨页**：消息页顶层改为**两段式 Tab：「通知 / 私信」**，通知段内再放一行 chip 筛选（全部 / 互动 / 订单 / 系统）。点击 4 宫格 = **切到通知段 + 筛到该类型**，零跳转 |
| 默认落在哪一段 | **私信段**。理由：tabBar 角标只统计私信未读 → 默认段必须与角标语义一致，否则用户进消息页发现"我的 3 条未读不在这里" |
| 通知中心二级页 `/pages/user/notifications` | **保留但降级为历史档案页**，从通知段右上角「全部 ›」进入，可搜索、可清空。现有 `?tab=` 参数能力保留 |
| 未登录态 | **同一个容器内的"未登录"占位段**，不跳到独立卡片、不换布局 —— 直接解决 team-lead 指出的"未登录卡片与登录后布局完全不同、切换时跳变" |

**理由**：两个入口的语义差异是真实的（通知 = 系统推送的、没有对话关系；私信 = 有对话关系、需要回复），合并成一个列表会让两类内容混在一起难以扫读（Phase 1 community 的问题正是此）。但"合并容器"（视觉一体）与"合并列表"（信息混排）是两回事 —— 本裁定取前者。

#### 2.4.5 全局角标规则汇总（一页速查）

| 规则 | 内容 |
|---|---|
| R1 | tabBar 角标**只有 messages 一个** |
| R2 | tabBar 数字 = **私信未读**，>99 显示 `99+` |
| R3 | 顶栏铃铛 = **红点，无数字**，数据源 = 通知未读总数 |
| R4 | 通知 4 宫格 = **红点**，无数字 |
| R5 | 订单带 = **小数字**，无红点 |
| R6 | 金色**不做角标**，只做身份语义 |
| R7 | 社区互动**不上 tabBar** |
| R8 | 角标出现/消失统一走 `uni.setTabBarBadge` / `uni.removeTabBarBadge`，**在 tabBar 页 `onShow` + WebSocket 事件 + 下拉刷新三处触发**（现状 `syncMessageTabBadge` 已具备，需扩到 5 页统一调用） |

> **R8 的实现风险**：`uni.setTabBarBadge` 在非 tabBar 页调用会 reject（`theme.js` 已注释说明）。因此角标同步必须放在 **App.vue 全局 + tabBar 页 onShow** 两处，或封装 `syncAllBadges()` 并在 `onShow` 统一调用。当前 `dmSocket.js` 的 `syncMessageTabBadge` 已在 App.vue 与 messages.vue 双调用，**其余 4 页需补 `onShow` 调用以清除残留角标**（切换 tab 时原生角标不自动清）。

### 2.6 Q6 · 四态的文案语气与落点

#### 2.6.1 中文文案语气规范（全局）

| 规则 | 说明 | ✅ | ❌ |

| R6 不用 emoji | 文案层 | 「已删除」 | 「删除成功 🗑️」 |

#### 2.6.3 错误态的重试粒度

**裁定：区块级（block-level）重试，不做整页级重试。**

| 层级 | 规则 |
|---|---|
| **区块划分** | 每页按**数据区块**独立管理 loading / error / empty 三态：<br>home → `hero` / `shelf`<br>community → `topics` / `feed`<br>messages → `notice` / `conv`<br>user → `member` / `wallet` / `social` / `order`<br>pet → `pet档案` / `care` |
| **失败影响面** | 一个区块失败**只重试该区块**，**不清空其它已渲染区块**（现状 messages 已按此实现，community / home / user 需对齐） |
| **区块重试的接口集合** | 该区块背后的一组接口（如 user 的 `wallet` 区块 = 优惠券数 + 收藏数两个接口 → 一次 `Promise.all`）。**不重新拉全页** |
| **何时才用整页级错误** | 仅当：**首屏必需区块**失败 **且** 无本地缓存 **且** 无兜底数据 **且** 该区块占据整屏。适用场景仅 2 个：home 的 `hero`、community 的 `feed`。其余一律区块级 |
| **错误条位置** | 区块**顶部**内联（Phase 1 §5.2.4 / §5.3.4 已定），`--state-error-surface` 底 + `--radius-md` + `luc-alert-triangle` 28rpx `--color-danger` + 26rpx 文字 + 右端文字按钮「重试」`--text-link`；margin 左右 `--gutter` |
| **错误条不遮挡** | 错误条**插入在流内**，不覆盖上方已渲染内容（Phase 1 §5.1.4 已定） |
| **网络错误与业务错误区分** | `isNetworkError`（`request.js` 已标记）→ 文案「网络似乎断了」；其他错误 → 「…加载失败」。**同一套视觉，只换文案** |

#### 2.6.4 是否需要独立离线态

**裁定：不做整页级离线态；做「区块级网络错误文案 + 首屏一条全局网络条」。**

| 项 | 裁定 | 理由 |
|---|---|---|
| 整页离线态 | **不做** | ① 需要引入全局网络监听与状态机，收益低于成本 ② 移动网络下"慢"与"断"体验连续，强行二分反而割裂 ③ 一旦引入"第四种状态"，容易与错误态叠加出第五种（离线 + 空） |
| 离线判据 | **复用 `request.js` 已有能力**：`isNetworkError` 标记 + `probeNetwork()`（`uni.getNetworkType`）。**不新增 `uni.onNetworkStatusChange` 全局监听** |
| 离线表达 | ① **区块级**：网络错误时区块错误条文案改为「网络似乎断了，检查连接后重试」；② **全局网络条**：仅在**首次进入 App / 页面首次加载失败且探测为无网络**时，在页面顶部显示一条细条（`--state-error-surface` 底 + `luc-wifi` 20rpx + 「当前无网络连接」+ 右端「重试」），**这是全局唯一的离线表达** |
| 兜底（若不做全局网络条） | 至少把所有区块的网络错误文案统一为「加载失败，请检查网络后重试」 |

## 3. 全局交互规范

### 3.1 导航与返回

#### 3.1.1 层级模型

```
L0  tabBar（5 个）：pet / home / community / messages / user
L1  二级页（navigateTo）：分类、会员中心、优惠券中心、限时特卖、通知中心、搜索、
                          帖子详情、商品详情、作者主页、订单列表、积分明细…
L2  三级页（navigateTo）：表单类（下单、编辑、发布）
```

| 规则 | 内容 |
|---|---|
| N1 | tabBar 页之间切换**必须** `uni.switchTab`，禁止 `navigateTo` |
| N2 | 从 L0 → L1 用 `navigateTo`；L1 → L2 用 `navigateTo`；L2 → L0 用 `navigateBack`（栈深为 1 时 `switchTab`） |
| N3 | tabBar 页**没有返回键**。L0 页内的"返回"语义 = 回到上一个 tab（系统行为） |
| N4 | 顶栏自绘返回按钮的二级页必须保证 `uni.navigateBack` 可用；栈深为 1 时降级为 `switchTab('/pages/tabbar/home')` |
| N5 | **登录页必须支持 `?redirect=`**（当前是硬伤，见 §3.5） |
| N6 | 二级页返回时**必须恢复来源页状态**：滚动位置、tab 选中态、已加载分页游标（见 §3.1.3 / §4.2.4 CC11–CC12） |

#### 3.1.2 下拉刷新

| 项 | 规范 |
|---|---|
| 触发方式 | **统一 page 级 `onPullDownRefresh`**，配 `pages.json` 的 `enablePullDownRefresh: true` |
| 适用页 | home / community / messages / user（现状 4 页已配）。**pet 不需要**（沉浸场景）、**category 保持现状**（其内容用 `scroll-view` 接管，页面级下拉不触发） |
| **user.vue 的双入口必须收敛为单入口** | 见 §5.1 |
| 刷新时的视觉 | **不清空旧内容**。顶部出现一条 2rpx 品牌色进度线（或沿用原生转圈），旧内容保持在位 |
| 刷新范围 | 只拉该页自己的区块。**不重置分页游标**（community 刷推荐流要重置 `feedCursor` / `feedSnapshotId`，这是例外且必要 —— 快照失效） |
| 结束 | 必须在 `finally` 中调用 `uni.stopPullDownRefresh()` |
| 最短展示 | 进度线最短可见 300ms，避免"闪一下" |

#### 3.1.3 触底加载

| 项 | 规范 |
|---|---|
| 触发 | page 级 `onReachBottom`；`pages.json` 的 `onReachBottomDistance` 设 **120**（默认 50 太晚，等用户滚到底才加载） |
| 适用页 | community（游标分页）、messages（页码分页）。home 现状是单页不真分页 → `onReachBottom` 保持空实现但**必须保留**（避免 uni-app 报错） |
| 加载中 | 底部 **3 点脉冲**（复用 `empty-state.vue` 已有 `.es-dot` 写法，`--color-primary`）。**不整页替换**（Phase 1 §5.2.4 已定） |
| 加载失败 | 底部 inline 小错误条 + 「重试」（与区块级错误条同款，宽度撑满容器） |
| 无更多 | 底部居中 24rpx tertiary 「— 已经到底了 —」+ 上方 1rpx `--divider-weak` 居中 120rpx 宽（Phase 1 §5.2.4 已定） |
| 并发保护 | 加载中标志位必须置位后才发请求（现状 `convLoadingMore` 已做，community 的 `loading` 需同样保护 `onReachBottom` 路径） |

#### 3.1.4 骨架屏

| 项 | 规范 |
|---|---|
| 出现时机 | **请求发出后 300ms 仍未返回**才显示骨架。快接口不闪骨架 |
| 消失时机 | 数据到达 → 骨架 **200ms 淡出**后再卸载（避免内容瞬跳） |
| 最短展示 | 骨架一旦出现，**至少停留 300ms**（避免 50ms 的"骨架一闪"，比不显示更糟） |
| 尺寸 | **必须与真实布局等高**（Phase 1 各页已给尺寸：Hero 16:9、Shelf 2 列 1:1、community 4:3、messages 88rpx 圆、user 会员卡 224rpx） |
| 文案 | **不出现**"加载中…"文字（Phase 1 X6）。但**语义上必须暴露给读屏**：`aria-busy="true"` + `aria-label` |
| 暗色 | `--skeleton-base` / `--skeleton-highlight`（Phase 1 §4.6 已定，highlight 不得超过 `#3C3732`） |
| 降级动效 | `prefers-reduced-motion: reduce` 时取消扫光动画，保留静态 `--skeleton-base` 底色 |
| 无障碍 | 骨架容器加 `aria-busy="true"`；读屏用户听到"加载中"而不是读到一个空页面 |

### 3.2 反馈机制（三分法）

#### 3.2.1 决策表

| 机制 | 判定条件 | 典型场景 | 规格 |
|---|---|---|---|
| **Toast**（轻提示） | 操作已完成 / 失败，**不需用户决策**，**不中断流程** | 已置顶、已删除、已加入购物车、已保存图片、已复制链接 | `uni.showToast({icon:'none', duration:1500})`；文案 ≤ 12 字；动词开头；**不用 `icon:'success'`**（原生 success 图标与品牌无关，Phase 1 约束 2 已注明 toast 图标无法定制 → 一律 `none`，成功感靠文案） |
| **Modal**（确认） | **破坏性 / 不可逆 / 涉及金钱 / 影响他人**，需要用户明确表态 | 删除会话、删除帖子、清空通知、结束客服会话、举报提交、退出登录 | 标题 = **动作问句**（「删除这条通知？」）；正文 = **后果**（「删除后不可恢复」）；按钮 = **动作词**（「删除」/「清空」/「举报」），**不用「确定」「取消」**；`confirmColor` 用**字面量**（约束 2：CSS 变量无效） |
| **Action Sheet**（动作表） | 同一对象上的 **2–5 个平行动作** | 帖子「⋯」（不感兴趣 / 举报 / 删除）、会话长按（置顶 / 删除）、举报原因选择 | 顺序 = **频率降序，破坏性垫底**；超过 5 项改中间页；`itemList` 文案 ≤ 6 字 |
| **Inline**（行内） | 状态变化但不需要独立反馈层 | 点赞变红、置顶图标出现、加载更多的脉冲点 | 复用 Phase 1 已定视觉 |

#### 3.2.2 破坏性确认的 confirmColor

| 场景 | `confirmColor` | `cancelColor` |
|---|---|---|
| 非破坏性确认（如"举报"提交） | 品牌金字面量：浅 `#8A7844` / 深 `#C9B47A`（Phase 1 约束 2 已定） | `#9A948C` / `#807A72` |
| **破坏性确认**（删除 / 清空 / 结束会话） | `--color-danger` 字面量：浅 `#C96E5F` / 深 `#D9836F` | 同上 |

> **说明**：Phase 1 约束 2 要求"原生组件处写字面量"，指的是**不能写 CSS 变量**；`--color-danger` 本身已是语义色，其字面量 `#C96E5F` / `#D9836F` 即符合"必须写字面量且是品牌/语义色"的要求。破坏性操作用红确认键是**语义正确性**要求，不是引入非品牌色。

#### 3.2.3 禁止事项

| # | 禁止 | 原因 |
|---|---|---|
| F1 | toast 承载需要用户决策的内容 | 决策不能一闪而过 |
| F2 | Modal 套 Modal | 层级混乱，Android 上易点错 |
| F3 | 同一操作同时给 toast + modal | 重复反馈 |
| F4 | ActionSheet 当错误提示用 | 错误提示用 toast / inline |
| F5 | 营销类弹窗用 Modal | 打断任务流，且 Modal 是"确认"语义 |
| F6 | 按钮写「确定」「好的」 | 动作词让用户知道会发生什么（Nielsen：好的关闭按钮文案） |

#### 3.3.3 长按的具体定义

| 项 | 规范 |
|---|---|
| 触发时长 | 350ms（沿用 uni-app `@longpress` 默认，**不自定义**） |
| 反馈 | 触发瞬间给**轻微视觉反馈**：目标行 `transform: scale(0.98)` + `--state-press` 底，160ms `ease-out`；若平台支持则 `uni.vibrateShort({type:'light'})`（**必须 try-catch 包裹**，不支持的端不报错） |
| 取消条件 | 长按期间手指位移 > 10px → 取消长按（视为滚动） |
| 长按后的 tap | 长按触发 Action Sheet 后，抬手产生的 tap 需在 300ms 内忽略（否则会同时进详情页） |

#### 3.3.4 方向仲裁规则（scroll-view 与手势打架的根治）

**这是 Phase 1 约束 4 的交互层解法。**

```
touchstart: 记录 (x0, y0)
touchmove:
  dx = x - x0, dy = y - y0
  if (!captured) {
    if (|dx| > 10px && |dx| > |dy| * 1.5)  captured = 'horizontal'   // 意图：横向手势
    else if (|dy| > 10px)                   captured = 'vertical'     // 意图：页面滚动 → 完全交还
    else                                     captured = null           // 未达判定，继续观察
  }
  if (captured === 'horizontal') { 接管手势，计算位移，双向 clamp }
  if (captured === 'vertical')    { 不做任何处理，完全交还页面滚动 }
touchend:   captured === 'horizontal' → 回弹动画 + 记录 justSwipedAt
```

| 规则 | 内容 |
|---|---|
| G1 | **只有判定为 horizontal 后才接管**。判定前不 `preventDefault`，不阻止滚动 |
| G2 | 阈值统一：`|dx| > 10px && |dx| > |dy| * 1.5`（现状 `messages.vue` 已实现，**保留**） |
| G3 | 垂直意图**完全不干预**——这是 Android touch-slop 陷阱的根因：任何在垂直方向上的 `preventDefault` / 自定义滚动都会触发 WebView 的惯性切断判定 |
| G4 | 同一时刻只允许**一行**会话处于展开态（现状 `closeSwipe()` 已实现） |
| G5 | 点击别处 / 点击已展开行 → **收起**而不是进入（现状 `onConversationTap` 已实现） |
| G6 | 页面纵向滚动**一律**由 uni-app page 原生接管，**不使用 `scroll-view scroll-y`**（约束 4） |
| G7 | 横向 `scroll-view` 三条硬规则（约束 4）：`white-space: nowrap` + 子项 `display:inline-flex`；条内不嵌 swiper；横向条与纵向滚动共存时纵向由原生接管 |
| G8 | **内层可点元素一律自身绑事件**（约束 4 末条）：头像、「⋯」、删除按钮都绑自己的 `@tap.stop`，不依赖父级冒泡。`scroll-view` 会吞 click，这是已知 APP 端行为 |
| G9 | 帖子卡**不做左滑**。原因：帖子卡的单击语义是"进详情"，左滑进详情在社区列表中极易误触；帖子操作统一走右上「⋯」 |

### 3.5 登录引导的统一拦截策略

#### 3.5.1 三档策略

| 档 | 触发时机 | 表现 | 例子 |
|---|---|---|---|
| **L0 静默** | 浏览不需账号的内容 | **完全不打扰** | home 全部、community 推荐流、帖子详情、商品详情、公开主页、搜索 |

**核心原则**：**页面进入不弹窗；动作触发才弹窗。** 这条同时解决了"user 页未登录仍渲染 0 值误导"与"未登录布局跳变"两个问题。

#### 3.5.2 L2 拦截 modal 的规格

| 项 | 规范 |

| 正文 | **说明为什么需要**（可选，1 句）：「点赞后作者会收到提醒」 |
| 按钮 | 「去登录」（confirm，品牌金字面量）/「再看看」（cancel，`#9A948C`） |

| **跳转方式** | **必须用 `uni.navigateTo`，禁止 `uni.reLaunch`**（见下） |
| **redirect 参数** | 必须携带当前页路径 + 触发动作，便于登录后回跳并**自动重放动作** |

#### 3.5.3 硬伤：登录后回跳丢失上下文

**现状（Phase 3 必须修）**：

| 位置 | 现状 | 问题 |
|---|---|---|

**裁定**：

| 规则 | 内容 |
|---|---|
| **R1** | 登录页支持 `?redirect=<encoded url>`（如 `/pages/tabbar/messages?from=login`） |
| **R2** | 登录成功后：有 `redirect` → 回该页；无 `redirect` → 回 home（保持现状兜底）。**⚠️ 回跳方式必须按目标是否 tabBar 页分两种，见下方「回跳方式的平台约束」** |

| **R5** | 禁止 `uni.reLaunch` 跳登录页。统一改 `uni.navigateTo` |
| **R6** | **登录后自动重放原动作**（如点了发布 → 登录 → 直接进发布页且**草稿内容保留**）。社区发布页的草稿必须按设备本地存，登录后读回 |

##### ⚠️ 回跳方式的平台约束（v1.1 新增 —— 读了 uni-app 官方类型定义后的硬发现）

**uni-app 官方类型定义（`@dcloudio/types/uni-app/uni/legacy/uni.d.ts`）原文：**

| API | 官方注释 | 能否带 query | 能否进 tabBar 页 |
|---|---|---|---|
| `navigateTo` | 「需要跳转的应用内**非 tabBar** 的页面的路径, 路径后可以带参数」 | ✅ 可以 | ❌ 不能 |
| `redirectTo` | 「需要跳转的应用内**非 tabBar** 的页面的路径, 路径后可以带参数」 | ✅ 可以 | ❌ 不能 |
| `switchTab` | 「需要跳转的 **tabBar** 页面的路径，**路径后不能带参数**」 | ❌ **不能** | ✅ 能 |
| `reLaunch` | 「需要跳转的应用内页面路径, 路径后可以带参数…**如果跳转的页面路径是 tabBar 页面则不能带参数**」 | ⚠️ tabBar 页不能带 | ✅ 能 |

> 行号：navigateTo 注释在 5278 行、redirectTo 在 5353 行、reLaunch 在 5372 行、switchTab 在 5391 行。

**这直接推翻了 R2 的朴素写法「`redirectTo` 回该页（tabBar 页需 `switchTab` + query）」—— `switchTab` + query 在 APP 端是无效的。**

**修正后的回跳方式（按目标页类型分两种）：**

| 目标页类型 | 例子 | 回跳 API | 参数怎么带 | 理由 |
|---|---|---|---|---|
| **非 tabBar 页** | `/pages/community/create`、`/pages/user/follow-list` | `uni.redirectTo({ url: redirect })` | **直接带在 URL 里**（`redirectTo` 允许 query） | 一条路径搞定，无副作用 |
| **tabBar 页** | `/pages/tabbar/messages`、`/pages/tabbar/user`、`/pages/tabbar/community` | `uni.switchTab({ url: '/pages/tabbar/messages' })` | **不能带 query** → 必须走 **storage 传递** | `switchTab` 官方明确禁止带参数 |

**tabBar 页的 storage 传递方案（项目里已有现成先例）：**

项目已有 `STORAGE_KEYS.BUYNOW_ITEM`（"立即购买临时单品:商品详情页直达结算用"）与 `STORAGE_KEYS.COMMUNITY_POST_DRAFTS` 两种"跨页带数据"的 storage 模式。沿用同一模式：

```js
// 1) 新增 storage key（建议加在 utils/storage.js 的 STORAGE_KEYS 里）
PENDING_LOGIN_REDIRECT: `${STORAGE_PREFIX}pending_login_redirect`,
// 值 = { url: '/pages/tabbar/messages', action: 'like', payload: {...}, ts: 1234567890 }

// 2) L2 拦截点：跳登录前写入
setStorage(STORAGE_KEYS.PENDING_LOGIN_REDIRECT, { url: currentTabUrl, action, payload, ts: Date.now() })

// 3) 登录成功：读出 → 若是 tabBar 页，switchTab 后由目标页自己消费
const pending = getStorage(STORAGE_KEYS.PENDING_LOGIN_REDIRECT)
// switchTab('/pages/tabbar/messages')  —— 不带 query

// 4) 目标页 onShow：消费并清除（一次性）
onShow() {
  const pending = getStorage(STORAGE_KEYS.PENDING_LOGIN_REDIRECT)
  if (pending && pending.ts && Date.now() - pending.ts < 5 * 60 * 1000) {
    removeStorage(STORAGE_KEYS.PENDING_LOGIN_REDIRECT)   // 必须清除，否则下次误触发
    if (pending.action === 'like') { /* 重放点赞 */ }
    if (pending.action === 'publish') { /* 进发布页，草稿已在本地 */ }
  }
}
```

| 规则 | 内容 |
|---|---|
| **R8** | **禁止 `switchTab` 带 query**（APP 端无效）。tabBar 页回跳一律用 storage 传递 |
| **R9** | storage 里的 pending redirect **必须带 `ts` 时间戳**，且消费时校验**有效期 ≤ 5 分钟**（防止用户登录后几小时再回看时被误触发） |
| **R10** | 消费后**必须 `removeStorage`**（一次性）。否则下次进页面会误触发上次的动作 |
| **R11** | `action` 白名单化：`like` / `publish` / `collect` / `dm` 等**已知动作**才重放；未知 action 一律忽略（防御性，避免 storage 被污染后触发意外行为）。⚠️ **storage 可被任意页写入**，这是白名单的必要性来源 |
| **R12** | 社区发布草稿：**已实现，无需新做**。`create.vue` 的 `readAllDrafts`/`writeAllDrafts` 已把 `content/topic/location/visibility` 存在 `STORAGE_KEYS.COMMUNITY_POST_DRAFTS`（30 天自动清理）。⚠️ 注释已写明「**本地图片路径无法持久化**」→ 登录回跳后**图片会丢** → 见 §3.5.4 |
| **R13** | 非 tabBar 页（如 `/pages/community/create`）**优先用 `redirectTo` + URL query**，不必绕 storage —— 只有 tabBar 页才需要 storage 兜底 |

#### 3.5.4 草稿图片丢失的提示（⚠️ 实施项，非仅验收项）

> **背景**：社区发布草稿**已经本地持久化**（`STORAGE_KEYS.COMMUNITY_POST_DRAFTS`，含 `content/topic/location/visibility`），所以"登录后草稿保留"这条**不需要新做**。
> **但**：`create.vue` 的源码注释已明确写「**本地图片路径无法持久化**」→ 登录回跳后**文字在、图没了**。

| 项 | 规格 |
|---|---|
| **何时触发** | 登录回跳进发布页时，检测到**草稿存在但 `images` 为空**（即回跳前有图、回跳后没了） |
| **提示形态** | ⚠️ **不是全屏错误、不是 toast**（toast 一闪而过，用户来不及反应；全屏错误过度）。用**发布页顶部一条 inline 提示条**：底 `--state-error-surface` + 圆角 `--radius-md` + `luc-alert-triangle` 28rpx `--color-danger` + 正文 24rpx `--color-text-secondary` + 右端文字按钮「重新选择图片」`--text-link` |
| **文案** | 「登录后本地图片无法保留，文字已保存，图片需重新选择」 |
| **动作** | 点「重新选择图片」→ 直接打开图片选择器（`onPickImage`），选中后追加到 `images` |
| **能否静默** | ❌ **不能静默丢图**。用户写了 500 字 + 配了 9 张图，回跳后只剩文字而无任何说明 → 会以为 App 吃掉了内容 → 信任崩塌 |
| **与社区错误条的一致性** | 与 Phase 1 §5.2.4 的社区 inline 错误条**同一形态**（`--state-error-surface` + `luc-alert-triangle` + secondary 正文 + `--text-link` 按钮），不另起一套样式 |
| **归属** | 视觉规格以本节为准；Phase 1 §5.2 标注「视觉沿用 Phase 2 定义」即可（发布页非 tabBar 页，不在 Phase 1 的 5 页规范范围内） |

> **Phase 4 实施清单条目**（不是验收项 —— 验收项是测试用的，实施清单才是干活的）：
> 1. 在 `community/create.vue` 的 `onShow` 中检测 pending login redirect 场景下的草稿恢复
> 2. 若草稿 `images` 为空但用户此前有图 → 渲染 §3.5.4 的提示条
> 3. 「重新选择图片」按钮接到既有的 `onPickImage`（**不要新写选择逻辑**）
> 4. 提示条在用户重新选图后自动消失

## 5. 实现约束下的可行性校验

### 5.1 约束 4 · `user.vue` 滚动方案：甲 / 乙 二选一

#### 5.1.1 裁定：**选乙（改原生 page 滚动）**

Phase 1 §4.1 已给出两方案的完整视觉规格差异，并注明"Phase 3 按 Phase 2 结论直接二选一落地"。我的结论是 **乙**。

| 维度 | 甲（保留 `scroll-view`） | **乙（原生 page 滚动）← 选定** |
|---|---|---|
| 滚动容器 | `height:100vh` 固定 | `min-height:100vh` 内容撑开 |
| 吸顶 | ❌ scroll-view 内 `position:sticky` 在 APP 端不可靠 → **账户条无法吸顶** | ✅ 账户条 sticky + veil-95 磨砂 |
| 首屏「账户条+会员卡」可见 | ❌ 不保证（`100vh` 在有 tabBar 时超出可视区，会把会员卡顶出首屏） | ✅ 保证（文档流前 432rpx 内） |
| tabBar 遮挡 | `padding-bottom: calc(112rpx + env(safe-area-inset-bottom, 0px))` | **完全相同**（两方案唯一共同必需项） |
| 下拉刷新 | 双入口（`refresher-enabled` + page 级） | 单入口 page 级 |
| 登录按钮 | 必须 `@click.stop` 兜底 | 可回归父级冒泡 |
| 与其余 4 页一致性 | ❌ home/community/messages 已是原生 | ✅ 一致 |

#### 5.1.2 选乙的 5 条理由

| # | 理由 |
|---|---|
| 1 | **消除双下拉入口补丁**。现状 page 级 + refresher 级两套并存是历史遗留；移除 scroll-view 后只剩一套，行为可预测 |
| 2 | **消除 scroll-view 吞 click 的历史 bug**。现状 `user.vue` 的登录按钮必须 `@click.stop` + 注释说明「scroll-view 会拦截 click」—— 移除后 workaround 可删 |
| 3 | **释放手势空间**。未来若加左滑 / 长按 / 横滑，scroll-view 内手势与滚动打架的问题不复存在 |
| 4 | **5 页滚动模型统一**（Nielsen 一致性） |
| 5 | **安全区可精确计算**。原生滚动下 `padding-bottom` 挂在页面根节点；scroll-view 内需额外处理内层高度 |

#### 5.1.3 甲方案的降级代价（若最终被迫选甲，需接受这些）

| 代价 | 影响 |
|---|---|
| 账户条**不能吸顶** | 与 home/community 顶栏行为不一致；用户滚动后失去身份锚点 |
| 首屏会员卡**可见性不保证** | Phase 1 §5.4.3「会员卡紧跟账户条（第二块），保证首屏可见（112+224+96 ≈ 432rpx 内）」这条焦点策略**失效** → P1「一屏一主角」被削弱 |
| 双下拉入口必须保留 | 需同时维护 `refresher-enabled` 与 page 级，且两者会**同时触发**（Phase 1 §4.1 明确指出） |
| 登录按钮 `@click.stop` 兜底不可删 | 保留一条已知的脆弱写法 |

> **结论**：甲方案会直接破坏 Phase 1 §5.4.3 的视觉焦点策略。这是选乙的决定性理由 —— 不只是"更好"，而是**甲与 Phase 1 已定的焦点策略冲突**。

| 纯图标按钮 | `aria-label` | i18n key。**必须**（`pageTitle.*` 已有现成 key 可复用：`pageTitle.communitySearch` `notifications.title` `pageTitle.communityCreate`） |
| 装饰性图标（luc-heart / luc-bookmark / luc-chevron-right 等） | `aria-hidden="true"` | — |
| 图片 | `alt` | uni-app `<image>` 支持 `alt` 属性（部分端）；商品图 `alt` = 商品名 |
| 骨架容器 | `aria-busy="true"` + `aria-label` = 加载中文案 | — |
| 状态区（toast / 错误条 / 空态） | `role="status"` + `aria-live="polite"` | 屏幕阅读器需**主动播报**状态变化（这是读屏用户唯一的状态反馈通道） |
| 错误条 | `role="alert"` | 错误需即时播报 |
| 未读会话行 | `aria-label` 追加「未读」 | — |
| 计数（购物车数 / 角标） | `aria-label` 含数字 | 视觉角标常被跳过，需在 label 里带上 |
| 列表 | `role="list"` + `role="listitem"` | 语义列表 |

**诚实说明**：uni-app 的 `aria-*` 属性在 **H5 与小程序生效**；**APP 端（app-plus）的无障碍支持依赖底层 WebView 与系统读屏（Android TalkBack / iOS VoiceOver），Vue 属性未必被原生读屏拾取**。因此：
- aria 属性**仍要写全**（成本低、为将来与 H5 服务）。
- APP 端的可达性主要靠**视觉设计本身**（对比度、触控区、字号）保证 —— 这也是 §6.2.1 / §6.2.3 权重更高的原因。

| 项 | 内容 |
|---|---|
| **结论** | ✅ **维持 8 项锁 / 3 项不锁**，但**调整锁的表现形式** |
| **8 项锁** | 签到 / 任务 / 邀请 / 会员 / 地址 / 宠物档案 / 收藏 / 足迹 —— 都需要账号才有意义 |
| **3 项不锁** | 帮助 / 设置 / 关于 —— **未登录也必须能改主题、语言、读隐私政策、读关于**。锁掉这些会让用户觉得"不登录连设置都用不了" |
| **⚠️ 呈现形式（已裁定采纳）** | **去掉 8 个锁图标**，改为**点击时才拦截**：<br>• 点击该行 → 弹 **L2 modal「登录后即可查看{该功能}」** +「去登录」/「再看看」；确认后跳登录页并带 `redirect`<br>• 未登录用户从列表本身**看不出哪些要登录**，但每个都能点到引导 —— 比"8 个锁图标"的心理负担小得多<br>• **例外（team-lead 强调的保留项）**：「设置」里的**主题 / 语言绝不拦截** —— 设备偏好与账号无关 |
| **理由** | 锁图标是**永久可见的负面提示**；按需拦截是**只在用户表达意图时出现**。Nielsen「识别优于召回」的反面 —— 用户不需要提前知道哪些需要登录，需要的是点了之后得到明确指引 |
| **⚠️ modal 文案要求（team-lead 补充的前提）** | 不加锁图标后，未登录用户**无法预判**哪些功能需要登录，会逐个试、每个都弹窗 —— **8 次弹窗反而更烦**。<br>→ 因此 **modal 文案必须统一为「登录后即可查看{该功能}」**，让用户知道**点对了、只是需要登录**，而不是被拒绝。<br>→ `{该功能}` 用功能名填充（如「签到」「我的地址」「宠物档案」），**不用泛称**（如「该功能」/「此内容」） |
| **原型同步** | Phase 3 原型需去掉 user 页未登录态的 8 个锁图标，改为「点击该行 → 弹 L2 modal」 |
| **如果团队偏好保留锁图标** | 则锁图标必须**只用 tertiary 色且不带斜杠**（Phase 1 §4.10：三级文字只用于非解释性元信息），且**点击行为必须是弹 modal 而非"点了没反应"** |
