# 0. 阅读方式与三层定义

## 0.1 三个行为等级（全文统一标记）

| 标记 | 定义 | 原型中的实现标准 |
|---|---|---|
| **真实现** | 原型内真的有状态变化，且状态可回退 | 必须有中间态与结束态，可反复操作 20 次不崩 |
| **模拟** | 有完整过渡动画，但终点是占位内容 | 必须给出"去处名"（如「→ 商品详情（占位）」），不许停在原地 |
| **仅提示** | 不产生导航，只给反馈 | Toast 1200ms / 底部动作表 / 二次确认弹窗 |

**禁止第四种**：点了没有任何反应（含"静默忽略"）。当前真实工程里存在 2 处静默忽略（见 §7.2），原型中一律改为「仅提示」。

## 0.2 与视觉规范的对齐约定

| 项 | 约定 |
|---|---|
| 时间/缓动 | 只用 visual-spec §2.7 的 `--dur-press 120ms` / `--dur-state 200ms` / `--dur-enter 280ms` 与两条 ease，不新增曲线 |
| 尺寸 | 所有几何写 rpx（750 设计宽）。原型按 `1rpx = viewportWidth / 750` 换算，禁写死 px（除 §4.4 标明的固定 px 项） |
| 触摸目标 | 一律 ≥ 88×88rpx，视觉本体可以小（chip 56、按钮 S 64），热区用透明 padding 补足，不用负 margin |
| 组件 | 只用 visual-spec §5 的 22 个 `My*`，新交互不得引入新视觉元件；缺组件需先回写 visual-spec |
| 色 | 文字只用 `--color-text` / `-secondary` / `-label` / `--ink-*`；金色实心块内只用 `--on-primary` |

# 1. 信息架构与 Tab 分工

## 1.1 五个 Tab 的唯一使命

每个 Tab 只承担一件事。使命里出现"也可以"就说明分工没对齐。

| Tab | 唯一使命（一句话） | 首屏第一条视线落点 | 第二落点 | 明确不在这里做的事 |
|---|---|---|---|---|
| **Pet** | 3 秒内知道「我的宠物今天需要我做什么」 | 场景中央的宠物形象（唯一视觉焦点） | 上叠的 Care Deck 第一列状态词 | 不做商品导购、不做社区信息流 |
| **Home** | 把「看看」变成「加购」 | Banner 主图（首屏唯一的图块） | 商品流第一张卡的价格 | 不做宠物档案、不做消息 |
| **Community** | 看别人的宠物 → 想晒自己的 | 帖子首图 | 互动行的点赞数 | 不做商品详情、不做私信列表 |
| **Messages** | 知道「谁在等我回」 | 第一条**未读**会话行（整行浅金） | 通知聚合卡的 4 个未读点 | 不做社交发现、不做群成员管理 |
| **User** | 确认「我的身份与资产到哪一步了」 | 会员卡积分数字 | 钱包 4 格的数字 | 不做信息流、不做搜索 |

## 1.2 跳转关系（受原生 tabBar 约束）

### 硬约束（不可绕过）

1. **底部 tabBar 是原生组件**：只能 `uni.switchTab`，**不能带 query**，会清空所有非 Tab 页的页面栈。
2. 因此**任何"带参数进入 Tab"的诉求都是非法的**。跨 Tab 传上下文只允许一种做法（§1.3）。
3. 页面内二级/三级一律 `navigateTo`。已从 tabBar 移出的 `pages/tabbar/category` 也走 `navigateTo`（路径里带 `tabbar` 只是历史包袱，不代表它是 Tab）。
4. **层级深度上限 3 层**：`Tab → 二级 → 三级`。禁止"列表页叠列表页"（如 社区 → 用户主页 → 帖子列表 → 帖子详情 已是 4 层，应改为详情内展开评论而非再跳）。

### 允许的跨 Tab 跳转（全站共 3 条，新增须走评审）

| # | 起点 | 终点 | 方法 | 说明 |
|---|---|---|---|---|
| X1 | Pet 快捷宫格「晒宠」（无宠物档案时） | Community 推荐流 | `switchTab('/pages/tabbar/community')` | 属"引导"，用户意图明确 |
| X2 | Home 金刚区「分类」 | `/pages/tabbar/category` | `navigateTo` | 分类已非 Tab 页 |
| X3 | 任意页的通知入口（铃铛） | `/pages/user/notifications` | `navigateTo` | 5 个 Tab 里 4 个有铃铛，落点必须同一个 |

**禁止**：从 Tab A 的二级页 `navigateTo` 到 Tab B（会叠栈且返回键行为错乱）。正确做法是先 `switchTab(B)`，再进 B 的二级。

### 跨 Tab 带上下文（X1 的通用解法，全站仅此一种）

```
写入方：uni.setStorageSync('tabIntent', { to: 'community', action: 'create', petId, ts: Date.now() })
跳转：  uni.switchTab({ url: '/pages/tabbar/community' })
读取方：onShow() 里读 tabIntent，校验 to 匹配 + ts 在 5s 内 → 消费后立即 removeStorageSync
```
过期判定必须是 **5 秒**：超过即丢弃，避免用户半天后回来被莫名拉进发布页。

**Community 的三条硬规则**
1. **话题 chip 是"导航"不是"筛选器"**：单击进话题详情页，不产生选中态。原型若做成"选中 chip 过滤当前列表"就与真实产品不符。
2. **点赞必须先动画后请求**（乐观更新）：动画立即开始，失败则回滚并 Toast「操作失败，请重试」。若先等请求再动画，弱网下会有 1–2s 的"点了没反应"。
3. **卡内多入口的冒泡隔离**：作者区、更多、点赞、评论、分享、图片都必须 stopPropagation，否则点一次点赞会同时进详情页。这是本页最容易实现错的一处。

## 3.1 五态命名与统一口径

## 3.4 切态不得改变几何（五态设计的硬前提）

「一键切 6 态不刷新」只有在**切态时页面不跳**时才成立。因此：

1. **骨架块高度必须复用真实卡高的同一套 token，不许估数字。** 准值（750 设计宽，375pt 基准）：

| 元素 | 真实高度 | 骨架必须同高 |
|---|---|---|
| 会话行 `skeleton-row` | **104rpx**（行高固定） | 圆 88rpx + 2 行文字块（60% / 40% 宽） |
| 商品卡 | **584rpx**（图 331 + 文字区 253；**完整 10 项清单与每项高度来源见 01 §4.2.2.2**，02 不另记） | 图 331 + 4 个文字块（78 / 39 / 36 / 24）+ 3 个 12rpx 间距 + 上下 20rpx 内距 = **584** |
| 帖子卡 头行 | **112rpx**（24 + 72 + 16） | 圆 72rpx + 2 行文字块 |
| 帖子卡 正文区 | **174rpx**（28rpx × 1.55 × 4 行） | 4 行文字块，行高 1.55 |
| 帖子卡 互动行 | **88rpx** | 3 个 88rpx 方形块 |
| 帖子卡 **卡总高** | **6 个档位 / 5 个不同高度**（4 图与 7–9 图同为 1044），见下方查表 | 骨架必须同值，不许用"一个通用值" |
| 空 / 错误 / 未登录态容器 | **≥480rpx**，上下 padding 96rpx | 三态共用同一几何 |

> **商品卡旧值 `≈548rpx` 是错的（02 v1.11 更正）**：`331 + 78 + 39 + 36` 少算了**评分行 24rpx + 它前面的间距 12rpx = 36rpx**。更根本的原因是**行盒口径没定义**——规范只写"价格 30rpx""评分 22rpx"，没写 line-height，于是同一个组件能解出 548 / 583 / 591 / 593 / 600 五个值，每个都"算得出来"。两个 override 已写死在 01 §4.2.2.2：**价格行 `line-height:1.2`（=36）、评分行 `line-height:24rpx`（= 图标高）**。验收按 **584**，实测 583 属 ±1rpx 容差，不报缺陷。

**帖子卡几何（定值，务必照抄）**

卡宽 686rpx（750 − 32×2）→ 媒体区 **638rpx**（686 − 24×2 图区内距）→ 图**不贴卡边**。
`卡总高 = 112(头行) + 图区 + 16 + 174(正文) + 16 + 88(互动)`。

> **正文行数变化时怎么换算**：按 01 §4.3.2.1 的「行数 → 卡高」小表（4 行 613 / 3 行 570 / 2 行 526 / 1 行 483 / 纯文本 319，行高 `28 × 1.55 = 43.4rpx`）。**02 不另记一组数**——同一件事写两处，改一处就分叉。

| 图片数 | 列 × 行 | 单 cell | 图区总高 | **卡总高** |
|---|---|---|---|---|
| 1 | 单图 `widthFix`（原图比例） | 638 × auto | **不固定** | **≈884rpx**（4:3 参考值，实际随原图比例浮动，见下方注） |
| 2 | 2 列 1 行 | 315 | 315rpx | **721rpx** |
| 3 | 3 列 1 行 | **207.33** | 207rpx | **613rpx** |
| 4 | **2 列 2 行** | 315 | 638rpx（2×315 + 8） | **1044rpx** |
| 5–6 | 3 列 2 行 | **207.33** | 422rpx（2×207.33 + 8 = 422.67） | **828rpx** |
| 7–9 | 3 列 3 行 | **207.33** | 638rpx（3×207.33 + 8×2） | **1044rpx** |

> **⚠️ 单图必须 `widthFix`，不要"修正"成 4:3**：`community.vue:947-954` 现有实现是 `mode="widthFix"` + `height:auto`，注释写明原因——**原先固定 480rpx，宽屏下宽度被拉长而高度不变，图片会被裁成扁条**。这是一次真实的历史修复，比"定值好看"重要。
> 因此上表的 **884rpx 只是 4:3 参考值**（用于估算与对照），真实单图卡高**随原图比例浮动**。**单图卡不参与 B 类等高要求**（§3.4.1）——B 类只要求"首卡顶边不跳、滚动不重置"，从未要求逐卡等高，而单图浮动正是 B 类允许的。若有人以"骨架对不齐"为由要求把单图改回固定 4:3，请驳回：那会推翻这次修复。

> **列数是样式属性，行数是内容属性 —— 所以只需三个类。** `grid-template-columns` 只决定列数；4 张图塞进 2 列会自动流成 2 行，2 张图塞进 2 列自然只有 1 行。因此 `col-2` **天然同时承载 2 张与 4 张**，不需要也不允许再造 `col-2x2`（它会与 `col-2` 逐字重复，只多一次"下游漏改第三个选择器"的机会）。
> **为什么 4 图必须走 2 列而不是 3 列**：若 `count >= 3` 统一走 3 列，4 图会渲染成 3+1，第二行右侧空出两个 cell 宽的洞，是信息流里最显眼的"未完成感"。列数不是张数的单调映射。
> **骨架不知张数怎么办**：首屏骨架渲染时数据还没到，**不可能预知每张卡是几图**。因此 `skeleton-post` 统一采用**3 图形态（613rpx）**作为代表形状（众数 + 中位高，误差双向摊薄），见 §3.4.1「两类切换」。

> ⚠️ 常见错法：按"3 列 = 3 × 220"算，图区高会多出约 39rpx，切态时整屏下跳。**cell 边长必须由 `calc()` 推导，禁止写死 207 / 315**：
> ```scss
> /* 媒体区 = 100vw − 64rpx(页面 gutter 32×2) − 48rpx(图区内距 24×2) = 100vw − 112rpx */
> .grid-col-2 { grid-auto-rows: calc((100vw - 112rpx - 8rpx) / 2); }   /* 315：2 图 1 行、4 图 2 行 */
> .grid-col-3 { grid-auto-rows: calc((100vw - 112rpx - 16rpx) / 3); }  /* 207.33：3 图 1 行、5–6 图 2 行、7–9 图 3 行 */
> ```
> 写死整数会让 1rpx 误差在 3 列时累积成右侧约 2rpx 的空白不齐，肉眼可见。另：`uni-image` 在 grid 内不响应 `aspect-ratio`，必须靠 `grid-auto-rows` 给行高 + 内层 `width/height:100%`（`community.vue` 现有写法正确，保留）。
>
> **⚠️ 公式的前置条件（必须同批改，否则等于没改）**：上面两个公式以「**页边距 32rpx（左右各 32）+ 图区内距 24rpx（左右各 24）**」为前提。现状代码是 `.feed{padding:0 16rpx}` + `.post-image-wrap{padding:0 20rpx}` → 只扣了 40rpx、漏掉页 gutter，实测 2 列 cell 为 **335×351（高 4.8%）**。若**只**把公式换成 112rpx 而不动页边距与内距，误差只会从 4.8% 降到 3.6%，看起来"改了但没对齐"，极易被误判成映射没生效。**页边距、内距、`grid-auto-rows` 三者必须一次改齐。**

> **7–9 图 = `1044`，与 4 图完全相同 —— 这是必然，不是巧合、也不是笔误。** 两种**满格**宫格都正好填满媒体区宽度，图区都是 **638 × 638 的正方形**：2 列 2 行 `315×2 + 8 = 638`，3 列 3 行 `207.33×3 + 8×2 = 638`。**只要填满，行数×列数怎么变，图区总高恒为 638。**
>
> **⚠️ 旧稿写的 `637 / 1043` 是错的（02 v1.10 更正）**，病根是"先把 `207.33` 取整成 `207` 再参与运算"：`3×207 + 16 = 637` → 卡高 1043。**必须全程用 `207.33`，只在最后输出时取整一次。** 这与 §7.3 写法铁律同族：先取整、再用结果去凑标注，差 1rpx 就会一路传下去。
>
> **取整口径**：表内一律取整到 rpx，**误差 ≤1rpx 属正常**。精确值已逐一复算（`cell3 = 622/3 = 207.3333`）：
> | 档位 | 精确卡高 | 记 |
> |---|---|---|
> | 2 图 | 721.0000 | 721（**精确**，无取整） |
> | 3 图 | 613.3333 | 613（floor） |
> | 4 图 | 1044.0000 | 1044（**精确**，无取整） |
> | 5–6 图 | 828.6667 | 828（floor） |
> | 7–9 图 | **1044.0000** | 1044（**精确**，无取整） |
>
> **注意：这张表里没有 ceil。** 满格宫格（4 图、7–9 图）的图区恒为 638、卡高恒为 1044，是**精确值而非"向上取整"**；只有 3 图与 5–6 图需要 floor。因此"实测必然出现 612 与 613 两种值"这个说法**在算术上不成立**——是否存在 1rpx 级差异取决于浏览器 subpixel 舍入，属实现侧现象，不属规范侧取整。
>
> **验收判据不用"命中某个整数"，用「同类卡片互相等高」+「骨架与真实卡同高」**——主理人处理商品卡即按此（骨架 583 == 真实卡 583 通过，不要求 == 584）。这样验收的人不必记容差数字。（01 §4.3.2.1 同口径）
>
> **来源式（与 01 §6.3 铁律 4「每项必须写出高度来源」对齐）** —— 上表五个整数都能由这三式自证，**不用记整数、记式子**：
> ```
> cell(3 列) = (638 − 8×2) / 3 = 207.33      cell(2 列) = (638 − 8) / 2 = 315
> 图区        = cell × 行数 + 8 × (行数 − 1)
> 卡高        = 112 + 图区 + 16 + 174 + 16 + 88
> ```
> 其中第一个 `638` 是媒体区宽度（750 − 64 页边距 − 48 内距），不是卡高；行数由张数自然流成（§3.4 三支映射）。
>
> **不要"修"这个同高**：用户在信息流里感知的是"几张图、多密"（2 行大方块 vs 3 行小方块），不是绝对卡高。要拉开就必须让 4 图用非 1:1 的 cell，那会拆掉 2 列与 3 列共用同一套 `grid-auto-rows` 的前提 —— 用几何去治内容分布的毛病不划算。

**⚠️ 实现待改（行为变更）**：`community.vue` 现为 `count <= 3 → col-2`，即 **3 图渲染成 2 列 2 行（图区 638rpx）**，与定值表「3 图 = 3 列 1 行（207rpx）」**单卡差 431rpx**。改为三支映射即可，**不新增任何 CSS 类**：

```
count <= 1                → 'single'   // ≈884（widthFix，浮动）
count === 2 || count === 4 → 'col-2'   // 721 / 1044
else                      → 'col-3'    // 613 / 828 / 1044
```

> **定性说明（避免被误记为"代码有 bug、规范是对的"）**：根因是 visual-spec 自身两处口径矛盾 —— §4.3.2 写「2–3 图 2 列」，§4.3.2.1 却按「3 图 = 3 列」给值；`community.vue` 恰好实现了前者。visual-spec **v1.4** 已修正自身矛盾并定五档（三支类 + 五个高度）。

2. **`guest` / `empty` / `error` 三态共用 `MyEmptyState` 的同一套几何**（图标 120rpx + 标题 28/600 + 描述 26rpx + 按钮 M 高 88rpx），只换图标与文案 → 三态互切零位移，原型演示时才不会露馅。
3. **数字位切态不许抖动**：`0` ↔ `—` ↔ 真实值 必须在同一容器内，`text-align: center` + `font-variant-numeric: tabular-nums`（数字 32rpx/600）。钱包 4 格、社交 4 格、订单角标全部适用。

### 3.4.1 两类切换要分开定义（否则"零位移"无法实现也无法验收）

| 类型 | 定义 | 要求 | 为什么 |
|---|---|---|---|
| **A 态间切换** `normal / empty / error / guest / stale` | 用户或开关驱动的状态变化 | **严格零位移**：同一容器、同一几何、同一 padding，只换图标与文案 | 这类切换用户会反复来回点（评审尤其会），跳一次就露馅 |
| **B 数据到达** `loading → normal`（骨架 → 内容） | 数据驱动，高度由真实内容决定 | **允许高度变化**，但须同时满足 ① `skeleton-post` 固定 3 图形态（613rpx，众数 + 中位高）② 内容淡入 200ms，不做高度补间动画 ③ 不重置滚动位置 ④ 首卡顶边不跳 | 首屏骨架渲染时**数据还没到**，不可能预知每张卡是几图，"骨架逐张等高"物理上做不到 |

**因此 §6.6 验收项"切态零位移"只针对 A 类**；B 类验收改为"骨架→内容无闪烁、滚动位置不被重置、首卡顶边不跳"。这条区分不清，Phase 3 会陷入"骨架到底该多高"的死循环。

> **B 类的两个明确豁免**：① **单图帖**（`widthFix`，卡高随原图浮动）**不参与等高要求**，只要满足"首卡顶边不跳 + 滚动不重置"；② 追加翻页（触底加载）也不受约束 —— 它不是切态，是追加。

# 4. 响应式与适配

## 4.1 rpx 换算基线（验收用）

| 设备宽 | 1rpx 实际 | 32rpx 页边距 | 88rpx 热区 | 28rpx 正文 | 56rpx 大数字 |
|---|---|---|---|---|---|
| 375pt（iPhone SE/8） | 0.5pt | 16pt | **44pt** ✓ | 14pt | 28pt |
| 390pt（iPhone 14） | 0.52pt | 16.6pt | 45.8pt | 14.6pt | 29.1pt |
| 430pt（iPhone 15 Pro Max） | 0.573pt | 18.4pt | **50.4pt** | 16pt | 32pt |

结论：**375–430pt 全区间无需任何断点改动**。88rpx 最小时 = 44pt（正好卡 HIG 下限），最大 50.4pt（不超标）。唯一需验的副作用是 430pt 下正文涨到 16pt、一行少约 12% 字数 → §5.3 给出防挤规则。

## 4.2 三档断点策略

| 档 | 范围 | 规则 |
|---|---|---|
| **T1 常规手机** | 320–430pt | rpx 原生比例。不改断点、不放大、不缩字。检查项：430pt 下标题/按钮是否换行 |
| **T2 大屏手机 / 小折叠内屏** | 431–600pt | 同上（rpx 继续按比例放大，最大约 ×1.6）。额外要求：所有单行文本容器必须有 `min-width: 0` + `white-space: nowrap` 或 `overflow: hidden`，防止 flex 子项被内容顶破 |
| **T3 折叠展开 / 平板 / 宽窗** | > 600px | **冻结 rpx 放大**，见 §4.3 |

## 4.3 >600px 宽屏策略（唯一推荐方案）

**核心决定：不追求"填满"，追求"比例不变"。**

1. 设 `h5.rpxCalcMaxDeviceWidth = 430`、`rpxCalcBaseDeviceWidth = 375` → 视口超过 430px 后 rpx 按 375 基准计算，不再继续放大。这样 750rpx 恒等于 375px，全站几何/字号/热区比例与手机完全一致。
2. 内容容器：`max-width: 750rpx`（= 375px）+ `margin: 0 auto`。**两侧留白由 Canvas 背景延伸**，不加边框、不加卡片。
3. 允许破例加宽的两个页面（仅此两个）：

| 页面 | >600px 容器 | 栅格 | 理由 |
|---|---|---|---|
| **Home 商品流** | `max-width: 1120px` | 2 列 → **3 列 / 4 列**（`repeat(auto-fill, minmax(300px,1fr))`）+ 卡间距 24rpx 不变 | 商品图越多越好扫 |
| **Community 信息流** | `max-width: 800px` | 帖子卡单列，卡内图片九宫格可升为 4 列 | 阅读宽度超过 560px 会掉眼 |

4. **明确不做**：双栏布局（左列表右详情）。Tab 页没有"选中项"概念，双栏会引入第二套焦点模型，收益不值。
5. **横屏**：全站锁定竖屏（`"pageOrientation": "portrait"`）。折叠屏展开属"变宽"不属"转横"，走 §4.3 第 1 条。

## 4.4 安全区与 tabBar 高度

### 顶部（唯一写法，沿用 visual-spec §3.4.4）

```scss
.safe-top / .nav-safe  →  padding-top: var(--sb)  /* --sb = max(--status-bar-height, env(safe-area-inset-top)) */
```
取 `max` 而非相加：iOS 上两者同为状态栏高，相加会翻倍。

### 底部（本文新增，务必按此拆分）

| Token | 值 | 用途 |
|---|---|---|
| `--tabbar-h` | `100rpx` | **仅作设计稿换算参考**（375pt 下 = 50px）。不用于定位计算 |
| `--tabbar-content-h` | `50px` | 原生/自绘 tabBar 的**固定内容高**。uni-app 原生 tabBar 是 50px 常量，**不随 rpx 缩放** |
| `--sab` | `env(safe-area-inset-bottom, 0px)` | 底部安全区**唯一简写**。必须先定义再使用——CSS 变量未定义会让整条 `calc` 在计算值阶段失效、回落 `auto`（FAB 会跟着文档流走，比数值错位严重得多） |
| `--tabbar-offset` | `calc(50px + var(--sab))` | 所有"以 tabBar 为基准"的定位与底部留白，**一律用这个** |

必须用 `--tabbar-offset` 的三处：

| 位置 | 写法 |
|---|---|
| Community FAB | `bottom: calc(var(--tabbar-offset) + 32rpx)`；`right: 32rpx` |
| 页面底部留白 | `padding-bottom: calc(var(--tabbar-offset) + 32rpx)`；有 FAB 的页面再 `+ 120rpx` |
| 底部动作表 / 半屏面板 | `padding-bottom: calc(24rpx + var(--sab))` |

**rpx / px 分工（与 visual-spec v1.1 §2.4 同一条规则，Phase 3 不得违反）**

| 类别 | 单位 | 例 |
|---|---|---|
| 自绘元素：布局、字号、圆角、间距、触摸目标 | **rpx** | `32rpx` 页边距、`88rpx` 热区、`--nav-h: 88rpx` |
| 客户端原生渲染且尺寸恒定：tabBar、状态栏、安全区 | **px** | `--tabbar-h: 50px`、`env(safe-area-inset-*)` |

`--tabbar-offset` **只承担"避开 tabBar"这一件事**，视觉间距继续用 rpx 相加。即 `bottom: calc(var(--tabbar-offset) + 32rpx)`；**禁止**把它折算成 `82px` 之类——否则宽屏下徽章/按钮与 tabBar 的相对呼吸感会变。

> ⚠️ **高风险（§7.1 R5）**：`position: fixed; bottom: 0` 在 H5 下被原生 tabBar 遮住（fixed 相对视口），但在 APP 下（webview 已扣掉原生 tabBar）就正好贴着 tabBar。两端同一数值必然有一端错 50px。验收方法：375×667 与 430×932 各测一次，FAB 底边到 tabBar 顶边应为 32rpx ± 2rpx，且 APP 真机不得出现约 50px 的空隙。仓库现状可佐证 uni-app **没有** tabBar 高度的内置 CSS 变量（`--window-bottom` 在 H5 被归一化为 `env(safe-area-inset-bottom)`，见 `pages/goods/flash-sale.vue` 注释），因此 50px 只能硬编码。

### iPhone 尺寸档（原型外壳必须支持）

| 档 | 视口 | safe-area-top | safe-area-bottom | tabBar-offset |
|---|---|---|---|---|
| A | 390 × 844 | 47px | 34px | 84px |
| B | 430 × 932 | 47px | 34px | 84px |

# 5. 无障碍

## 5.1 焦点顺序（键盘 Tab 序列）

原则：**视觉顺序 = DOM 顺序 = 焦点顺序**，禁 `tabindex > 0`。每页首焦点为顶栏第一个操作按钮，末焦点为最后一个可交互行；页脚品牌行不可聚焦。

| 页面 | 焦点序列 |
|---|---|
| **Pet** | 宠物头像 1..n → 装扮 → 3D 空间 → 护理列 1..3 → 提醒行 → 提醒 `⋯` → 快捷 1..5 |
| **Home** | 搜索条 → 扫码 → 通知 → 金刚 1..4 → Banner 当前页 → 推荐 Tab 1..3 → 商品卡 1..n（卡内无第二焦点） |
| **Community** | 搜索 → 通知 → Tab 1..3 → 搜索条 → 话题 chip 1..n → 帖子卡 1..n（每张卡内：作者 → 更多 → 点赞 → 评论 → 分享）；**FAB 放在 DOM 末尾**（视觉右下但焦点最后，避免打断信息流） |
| **Messages** | 铃铛 → 群聊 → 发起 → 通知格 1..4 → 发起私信(区块头) → 会话行 1..n（行内：会话本体 → 删除按钮，删除按钮仅展开时进入序列） → 加载更多 |
| **User** | 头像行 → 会员卡 → 钱包 1..4 → 社交 1..4 → 全部订单 → 订单 1..4 → 功能 1..7 |

弹层出现时：焦点移入弹层首个可点项，`Escape` / 点遮罩关闭，关闭后焦点**回到触发元素**。

## 5.2 可点击语义与 `aria-label` 中文口径

图标按钮一律无可见文字，必须有 `aria-label`。以下为**逐字口径**，不得自创：

| 位置 | `aria-label` | 备注 |
|---|---|---|

列表语义：会话组 / 帖子流 / 功能列表用 `role="list"`，其直接子项 `role="listitem"`；Tab 组用 `role="tablist"` + `role="tab"` + `aria-selected`。

**图标载体唯一合法形式：`luc luc-xxx` 图标字体。** 禁止 emoji、禁止内联 `<svg>`、禁止 data-URI 占位图。三条硬理由：

| 禁止项 | 后果 |
|---|---|
| **emoji 当图标** | `LucideIcons` 字体无 emoji 字形 → **图标渲染为空**。真实故障：`user.vue:158/159/163` 的 `💳 🛒 📦` 未进 `EMOJI_MAP`，订单 3 个格子图标全空 |
| emoji 的语义不一致 | 同一 emoji 在不同系统字体下形状/配色各异，破坏视觉一致性；且无法通过 `aria-label` 之外的方式统一语义 |
| 内联 `<svg>` / data-URI | APP 端部分机型不渲染；且无法复用图标字体的大小/颜色继承 |

> **不得假设 `EMOJI_MAP` 能兜住**：`utils/lucide.js` 的 `EMOJI_MAP` 有 138 项，看起来像一套完整兜底，实际未命中时 `$luc()` 返回的是 `luc-💳` 这种**非法类名**——不报错、不告警，只是渲染成空洞。所以本条的**验收方式不是"搜 emoji"，而是"每个图标位都要看见图形"**：搜索式验收只要有人换个写法（`&#128179;`、变量拼接、背景图）就会漏；只有逐位数图形，才拦得住。

## 5.3 动态字号（系统字号放大 1.3× 不破版）

前提：`rpx` 不随系统字号变化，但 WebView/原生会把 `font-size` 再乘系数。约束如下：

| # | 约束 | 具体做法 | 验收 |
|---|---|---|---|
| 1 | 容器高度不得写死到"刚好装一行" | 列表行 `height:104rpx` → 改 `min-height:104rpx`；按钮 `height:88rpx` → `min-height:88rpx` + 上下 padding | 1.3× 下无文字被裁 |
| 2 | 禁用 `overflow: hidden` 裁文字 | 只允许用 `-webkit-line-clamp`（本身会出省略号），其余容器不加 `overflow:hidden` | — |
| 3 | 截断行数给余量 | 帖子正文 4 行 → 1.3× 下仍按 4 行截断，但行高固定 `1.55` 倍数不写死 px | 截断处出现 `…` 而不是切掉半行 |
| 4 | 角标/数字底线 | 22rpx 为最小字号；1.3× 下 = 28.6rpx；角标 pill 用 `min-width` + `padding: 0 8rpx`，不写死宽 | 99+ 不溢出 pill |
| 5 | 5 列宫格保底 | 快捷宫格 5 列时标签可能换行 → 用 `-webkit-line-clamp:1` + `min-height: 2 行高` 让 5 列等高 | 5 项底部对齐 |
| 6 | tabBar 文字不放大 | 原生 tabBar 不受页面字号影响，**这是刻意的**；自绘 tabBar 也要用固定 px 字号，否则与原生不一致 | 切 Tab 时底栏不跳 |
| 7 | 横向 chip 条 | chip 文案放大后高度会溢出 56rpx → chip 用 `min-height:56rpx` + `line-height:1.4` | chip 不裁字 |

## 5.5 对比度复检（落到 token，不再复述色值）

- 全部正文/标签文字对比度 ≥ 4.5:1：靠 `--color-text` / `-secondary` / `-label` / `--ink-*` 保证，**禁止** `--color-text-tertiary` 承载信息（只有 2.70:1）。
- 可交互控件边界（输入框、chip 描边、Tab 下划线）≥ 3:1：用 `--color-line-strong`，不用 `--color-divider`。
- 金色文字只用 `--ink-gold`（5.83:1）；金色实心块内只用 `--on-primary`（8.52:1）。
- 护理状态条 4rpx 是纯装饰（语义由文字承担），不参与对比度验收。

## 5.6 动效降级

`prefers-reduced-motion: reduce` 时：关闭骨架扫光（改静态色块）、关闭粒子脉冲、点赞弹跳改 120ms 色变、左滑回弹改瞬时、Banner 自动播放**关闭**（仅手动）。

## 7.3 本文档与上游 / 下游的对齐说明

1. **`--tabbar-h` 的用法收窄（已同步 visual-spec v1.1）**：visual-spec 原定义 `--tabbar-h: 100rpx` 并用于 FAB 定位。本文补充：原生 tabBar 是 50px 常量，`100rpx` 只在 375pt 宽成立；定位一律改用 `--tabbar-offset`。visual-spec v1.1 已改为 `--tabbar-h: 50px` 并新增「rpx / px 分工」规则，**两文档现已一致**。
2. **组件不新增**：本文用到的所有元件均来自 visual-spec §5（`MyEmptyState` / `MySkeleton` / `MySwipeAction` / `MySheet` / `MyButton` / `MyBadge` / `MySegmentedTabs` / `MySearchBar` / `MyNavBar` / `MyChip`）。动作表（ActionSheet）视觉沿用 `MySheet`，新增的只是"行为"不是"外观"。
3. **文案口径**：所有关键文案以本文档 §2/§3 的中文为准（比现有 i18n 更短、都带下一步动作）；落地时需同步回写 i18n，不在组件里硬编码。
4. **帖子卡几何以 visual-spec §4.3.2.1 为准**（现 v1.11）：卡宽 686rpx、媒体区 638rpx（图不贴卡边，左右各 24rpx 内距）；**三个类** —— `single`（`widthFix`，卡高浮动，4:3 参考 ≈884）/ `col-2` 721（2 图）与 **1044**（4 图）/ `col-3` 613（3 图）、828（5–6 图）、**1044**（7–9 图）。**7–9 与 4 图同高是必然**（两种满格宫格图区都是 638×638），不是巧合。**不设 `col-2x2`**（列数是样式属性、行数是内容属性，`col-2` 天然承载 2 张与 4 张）。本文 §3.4 已同步，并更正了"代码与规范冲突"的定性。
5. **「历史修复 vs 规范定值」的裁决顺序**：出现冲突时**默认先给代码一个举证机会**，但**给举证机会 ≠ 默认代码对**。唯一判据是「**可复现的失败路径 > 任何一方的权威**」——本轮的单图 `widthFix` 之所以推翻定值表，是因为 `community.vue:947-954` 的注释写明了"宽屏下宽度被拉长、高度不变，图片被裁成扁条"这一**具体失败场景**；若某处代码只是惯例写法、或注释只写"这样更好看"，则定值表优先，不论它是代码还是规范。

> **附带一条写法铁律（本轮踩过两次）**：凡是写进"目标值 / 可照抄"位置的**构成式，不许省略任何加数**。`112 + 图区 + 174 + 88` 与 `112 + 图区 + 16 + 174 + 16 + 88` 差 32rpx，而两者都可能以"→ 613"结尾，读者无法自证，只能照抄。要简写就写 `581 + 16×2`，**别把加数抹掉**。同理，差额式（"减掉 A+B+C 正好 D"）也必须每一项都对得上，否则下游会拿它去自检。

## 7.5 对外沟通口径：Community 信息流会变密（设计意图变更，非 bug）

| 张数 | 旧 列/图区/卡高 | 新 列/图区/卡高 | 差 |
|---|---|---|---|
| 1 | 1 / 478 / 884 | 1 / 478 / 884 | 0 |
| 2 | 2 / 315 / 721 | 2 / 315 / 721 | 0 |
| 3 | 2 / 638 / 1044 | **3 / 207 / 613** | **−431（变密）** |
| 4 | 3 / 422 / 828 | **2 / 638 / 1044** | **+216（变疏）** |
| 5–6 | 3 / 422 / 828 | 3 / 422 / 828 | 0 |
| 7–9 | 3 / 638 / 1044 | 3 / 638 / 1044 | 0 |

**结论：只有 3 图帖变密，4 图帖反而变疏，其余不变。** 以长图集为主的 feed 观感几乎不变。

**对外一句话口径（合并表述，供产品/前端/QA 复用）**：
> **「2 或 4 图用 2 列，其余多图用 3 列。」**

比上面那张成本表好传播，且不会把"3 图变密 / 4 图变疏"两个相反方向说成一个。**对内**必须仍用上表逐张对照，因为这句话只讲列数、不讲卡高，无法单独支撑回归验收。
（表中「1 图」行的 884 是 4:3 参考值；真实单图用 `widthFix`，卡高随原图比例浮动，改前改后均为浮动，故差值记为 0。）

**若 product 要求"调矮/调密"，按杠杆顺序取，必须止步于 ④（visual-spec v1.5 §4.3.2.1）**：

| 序 | 杠杆 | 收益 | 风险 |
|---|---|---|---|
| ① | 正文行数 4→3 | −43rpx/卡 | 信息量减少，需产品确认 |
| ② | 头行内距 24/16→16/12 | −12rpx/卡 | 头像略挤 |
| ③ | 图区上下间距 16→12 | −4rpx/卡 | 几乎无感 |
| ④ | 卡间距 24→16 | −8rpx/张 | 卡组感变弱 |
| ✗ | **改 cell 比例（4:3 / 4:5）** | — | **禁止**：2 列与 3 列将无法共用 `grid-auto-rows`，网格地基被拆 |

> **"把 4 图帖做矮一点"的答案不是动图区，是动 ①–④。cell 永远 1:1，不在可调项内。** 4 图帖现在比原来高 216rpx，一定会有人说"太长"；届时第一个被想到的解法就是"把图缩小"，那会把整套一致性拆掉。此与前端实现错误无关；前端按 v1.6 落地后应留差异截图备查。
