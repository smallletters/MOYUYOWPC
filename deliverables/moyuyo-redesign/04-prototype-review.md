### P0-2 ｜ Community 关注 / 话题 tab：三态都卡在骨架，搜索区也一起没了

**证据**（切到「关注」后逐态取样）

| 态 | `posts` | `#cmList` 内容 | `.page` 子块（px） |
|---|---|---|---|
| normal | 0 | 恒为 `.sk-card` 骨架 | nav 46 · tabs 46 · **feed 673** |
| guest | 0 | 与 normal **DOM 完全相同** | 同上 |
| empty | 0 | 与 normal **DOM 完全相同** | 同上 |

- 「关注」与「话题」两个页内 tab，在三个状态下渲染的是**同一段骨架**，永不切出内容
- 同时**搜索条 + 话题 chipbar（92px）消失**（对照：推荐 tab 有这块）

**期望值**
- 关注 tab：normal 出帖子 / **guest 出登录卡**（§3.3 列为 P0 第一条：「关注流需要登录 / 登录后查看你关注的人的动态」+ 主按钮「去登录」）/ empty 出「还没有关注的人，去发现感兴趣的用户吧～」
- 话题 tab：empty 出「选择上方话题标签查看帖子」
- 搜索条在三个页内 tab 里都保留 —— 它不依赖接口数据

> **这条的性质不是"完成度不够"，是"验收失效"。** 空态没做，属于少画一屏；三态未分离，属于**最该被看见的那个态看不见**。§3.3 把「Community 关注流 `guest`」排在 P0 第一条，理由写在 §3.1 里——现状工程把"未登录"显示成"你没有关注任何人"，是**最伤用户的一处**。我们现在做的正是修它，而原型恰好把这一屏藏在一段永不结束的骨架后面：**修一个用户看不见的 bug，和一个演示不出来的修复，价值差不多。**
>
> 评审那天若有人问"未登录的关注流长什么样"，目前唯一的答案是"演示不出来"。这一条建议列进 Phase 3 的**进门条件**，不是收尾项。

### P0-4 ｜ Pet `empty` / `guest`（含 `loading`）：Care Deck 下移 32rpx（A 类零位移被破坏）

**证据**（以 scene 顶边为基准，单位 rpx）
| 态 | `.care` 顶边 | `.care` computed `margin-top` |
|---|---|---|
| normal | **688**（= scene 720 − 32，靠 `.scene{margin-bottom:-32rpx}` 咬合） | `0px` |
| empty | **720** | **16.64px = 32rpx** |
| guest | **720** | **16.64px = 32rpx** |

**期望值**

- 场景与护理卡的咬合只由 `.scene` 的负 margin 决定，**子块不得再补 margin-top**（一处内联 style 影响三态，删掉即可）

### P0-5 ｜ 骨架卡没有用定值：Community 差 198rpx，Home 同屏两种高度

**证据 A：Community `skeleton-post`**（两侧都是**逐块实测**，各自加得起来）

| 段 | 实测（合计 415rpx） | 定值（合计 613rpx，§3.4 3 图档） |
|---|---|---|
| 卡内距 上 | 24 | 0 |
| 头行 | 72 | **112** |
| 行间 | 16 | 16 |
| 图区（3 列 1 行） | 207 ✅ | 207 |
| 行间 | 16 | 16 |
| 正文 | 24 | **174（4 行文字块）** |
| 行间 | 8 | —— |
| 正文 | 24 | —— |
| 互动条 | **0（缺失）** | **88** |
| 卡内距 下 | 24 | 0 |
| **合计** | **415** | **613** |

**差额怎么读**（按项拆，别按总数猜）：

| 项 | 骨架 | 定值 | 差 |
|---|---|---|---|
| 块高合计 | 72 + 207 + 24 + 24 = **327** | 112 + 207 + 174 + 88 = **581** | **−254**（正文 −126 / 互动 −88 / 头行 −40） |
| 行间合计 | 16 + 16 + **8** = **40** | 16 + 16 = **32** | **+8** |
| 卡内距 | 24 + 24 = **48** | 0 | **+48** |
| **合计** | **415** | **613** | **−198** |

> **不要用"613 − 415 = 198，减掉几块就对上了"这种差额式去自检** —— 两边不是同一套加法（骨架多 48rpx 卡内距、多 8rpx 行间，把缺口抵掉了一部分）。要定位就逐块量这三处：**正文 48 vs 174、互动 0 vs 88、头行 72 vs 112**。（此条已写进 02 §7.3 作为写法铁律）

**证据 B：Home `skeleton-product`**
- 共 **5 张**（§3.2 定 **4 张**）
- 同屏两种高度：首张 **386rpx**，其余 4 张 **491rpx**（01 §4.2.2.2 定 **584rpx**，±1rpx 容差；同为实测的真实卡高 583rpx）
- 同一行两张不等高 → 首行右侧留空

**期望值**
- Community：**613rpx**，且必须含互动条（否则数据到达时卡突然长出 88rpx）
- Home：**4 张 × 584rpx**，同屏等高（真实卡实测 583rpx = 303.2px，与定值差 1rpx，属容差）
- 骨架只允许"内容块数量少"，不允许"总高不对"——B 类允许高度变化，但**定值本身是可验收项**
